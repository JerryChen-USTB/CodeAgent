# 待办事项管理系统 PRD

## 1. 产品概述

待办事项管理系统是一款面向个人用户的离线任务管理应用。用户主要在终端中使用它记录、查看、完成和删除日常任务。产品第一版不追求复杂协作、提醒通知或联网同步，而是强调“打开一次程序，在同一个运行会话中完成多次操作”的真实软件体验。

本案例要求智能体从空 `workspace/` 开始实现完整 Python 项目。最终成品应当像正常软件一样可交互使用：用户运行一次程序后进入简单文本 TUI 菜单，在同一个会话里完成添加、查看、标记完成、删除和退出。不能只依赖“一次一个 shell 命令”的操作方式。

## 2. 产品目标

- 支持用户在一个连续的终端会话中管理多个待办任务。
- 使用本地 UTF-8 JSON 文件保存数据，保证关闭程序后任务仍然存在。
- 通过菜单、提示语和确认信息降低记忆命令参数的成本。
- 支持键盘输入和标准输入重定向，便于用户手动使用，也便于自动化测试。
- 仅使用 Python 3.11+ 标准库实现，保证环境准备简单。

## 3. 用户画像

### 3.1 安排每日学习任务的学生

学生早上打开终端，启动待办事项管理系统，连续录入“完成实验报告”“复习课堂笔记”“购买笔记本”等任务。部分任务有截止日期和高优先级。学生希望能快速查看当前未完成任务，并在完成后立即标记为 done。第二天再次打开同一个任务文件时，已完成状态和未完成任务都应保留下来。

### 3.2 跟踪小型项目事项的开发者

开发者希望在编码时维护一个小清单，例如“实现解析函数”“补充边界测试”“更新 README”。他们不希望打开浏览器或登录账号，只想在项目目录旁边启动一个轻量终端程序。开发者希望 JSON 文件结构清晰，在需要排查问题时可以直接打开查看。

### 3.3 自动化评测人员

课程评测脚本会以 subprocess 方式启动程序，通过 stdin 连续发送菜单选项和输入内容，然后检查 stdout、stderr、退出码和 JSON 文件。因此 TUI 不能依赖鼠标、全屏终端、复杂方向键事件或只能人工操作的界面。简单的“打印菜单 + 读取一行输入 + 执行动作 + 回到菜单”即可满足要求。

## 4. 核心交互体验

### 4.1 默认启动方式

用户运行：

```bash
python -m todo_manager --file tasks.json
```

程序应进入交互式文本菜单。启动后 stdout 应包含产品名称和主要操作，例如：

```text
Todo Manager
Data file: tasks.json
1) Add task
2) List tasks
3) Mark task done
4) Delete task
5) Exit
Choose an option:
```

具体排版可以不同，但必须清晰暴露这五类动作：添加任务、查看任务、标记完成、删除任务、退出程序。

### 4.2 会话式操作要求

用户在同一个程序进程中可以连续完成多个操作。示例输入流：

```text
1
Write report
2026-06-10
high
2
open
5
```

程序应按顺序理解为：添加任务、填写标题、填写截止日期、填写优先级、查看 open 任务、退出程序。整个过程不应要求用户重新运行 shell 命令。

### 4.3 关于一次性命令

可以保留可选的一次性命令作为兼容能力，例如 `add`、`list`、`done`、`delete` 子命令；但这不是本 benchmark 的核心验收目标。默认只传入 `--file` 时必须启动交互式 TUI。若成品只能通过一次一个命令操作，则不满足本案例要求。

## 5. 功能需求

### F-01 启动应用

当用户执行 `python -m todo_manager --file tasks.json` 时，系统应：

- 解析 `--file` 参数。
- 如果任务文件不存在，将任务列表视为空。
- 如果任务文件存在，读取并解析 JSON。
- 如果 JSON 无法解析或结构非法，启动失败，退出码非 0，并向 stderr 输出包含 `invalid task file` 的错误。
- 数据加载成功后进入主菜单循环。

### F-02 添加任务

用户在菜单中选择 `1` 或 Add task 动作后，系统依次提示：

1. 任务标题。
2. 截止日期。
3. 优先级。

输入规则：

- 标题必填，去除首尾空白后不能为空。
- 截止日期可为空；空值表示无截止日期。
- 非空截止日期必须符合 `YYYY-MM-DD` 格式。
- 优先级可为空；空值表示 `normal`。
- 非空优先级只能是 `low`、`normal`、`high`。

业务规则：

- 新任务状态必须为 `open`。
- 第一个任务 ID 为 `1`。
- 后续新任务 ID 使用当前任务文件中最大 ID 加一。
- 成功后 stdout 必须包含 `created task #<id>: <title>`。
- 添加失败时不得写入半成品任务。

### F-03 查看任务

用户在菜单中选择 `2` 或 List tasks 动作后，系统提示状态过滤条件：

- 空输入或 `all`：显示全部任务。
- `open`：仅显示未完成任务。
- `done`：仅显示已完成任务。

展示规则：

- 按任务 ID 升序输出。
- 没有任务或没有匹配任务时，输出 `no tasks`。
- 每个任务一行，格式如下：

```text
#<id> [<status>] <priority> <title> due <date-or-none>
```

示例：

```text
#1 [open] high Write report due 2026-06-10
#2 [done] normal Buy milk due none
```

### F-04 标记任务完成

用户在菜单中选择 `3` 或 Mark task done 动作后，系统提示输入任务 ID。

规则：

- ID 存在时，将任务状态设置为 `done`。
- 已经是 `done` 的任务再次标记完成时仍然成功，不创建重复任务。
- 成功后 stdout 必须包含 `completed task #<id>: <title>`。
- ID 不存在或无法解析为整数时，输出包含 `task not found` 的错误，并回到菜单。

### F-05 删除任务

用户在菜单中选择 `4` 或 Delete task 动作后，系统提示输入任务 ID。

规则：

- ID 存在时，从任务列表中删除该任务。
- 成功后 stdout 必须包含 `deleted task #<id>: <title>`。
- ID 不存在或无法解析为整数时，输出包含 `task not found` 的错误，并回到菜单。
- 删除操作成功后必须立即持久化。

### F-06 退出应用

用户输入 `5`、`q`、`quit` 或 `exit` 时，程序应正常退出，退出码为 0，并输出简短告别语，例如 `goodbye`。如果 stdin 到达 EOF，程序也应在处理完已有输入后正常退出，不能无限等待。

### F-07 输入错误恢复

交互过程中出现可恢复错误时，程序不应崩溃，不应打印 Python traceback，而应输出清晰错误并回到主菜单。

必须包含的错误关键词如下：

| 场景 | 错误关键词 |
| --- | --- |
| 标题为空 | `title is required` |
| 日期格式错误 | `invalid due date` |
| 优先级非法 | `invalid priority` |
| 状态过滤值非法 | `invalid status` |
| 任务 ID 不存在或非法 | `task not found` |
| JSON 文件无法解析 | `invalid task file` |
| 未知菜单选项 | `unknown option` |

## 6. 数据需求

任务文件为 UTF-8 JSON，顶层为数组。每个任务对象至少包含：

```json
{
  "id": 1,
  "title": "Write report",
  "status": "open",
  "priority": "high",
  "due": "2026-06-10"
}
```

对于没有截止日期的任务，JSON 中 `due` 应为 `null`，在 TUI 中显示为 `none`。

保存要求：

- 使用两个空格缩进。
- 使用 `ensure_ascii=False` 保留中文。
- 保存时按 ID 升序排列。
- 正常操作中应避免写出半截 JSON。推荐写入临时文件后替换目标文件。

## 7. 非功能需求

- Python 版本：3.11+。
- 依赖范围：仅 Python 标准库。
- 支持 Windows、Linux、macOS 终端。
- TUI 使用普通文本输入输出即可，不要求 ANSI 色彩或全屏界面。
- stdin 重定向时必须可运行，不能依赖真实 TTY。
- 模块职责应清晰分离：存储、业务逻辑、校验、TUI 控制器尽量不要混在一个巨大函数里。
- 错误信息应简洁、稳定、可被自动化测试断言。

## 8. 非目标

- 不做用户登录和权限。
- 不做网络同步和云备份。
- 不做提醒通知、循环任务和日历集成。
- 不做 Web、桌面 GUI 或移动端。
- 不做多用户协作。
- 不要求复杂全屏 TUI。

## 9. 验收摘要

本案例通过隐藏 oracle 测试验收。验收重点包括：

- 默认入口能启动交互式 TUI。
- 用户能在一个运行进程中完成完整任务生命周期。
- JSON 持久化能跨会话保存数据。
- 输入错误不会导致程序崩溃。
- 自动化测试能通过 stdin 驱动 TUI，并检查 stdout、stderr、退出码和 JSON 文件。
