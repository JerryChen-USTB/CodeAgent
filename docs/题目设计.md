# 一、选题说明
---
## 1. 基于大语言模型的软件工程智能体

### 1.1 项目目标

在当今软件工程领域，利用大语言模型辅助软件开发已成为新一代工程实践的核心趋势。然而，通用大模型在复杂、多阶段软件项目中的自主性与稳定性仍有较大提升空间。本课程设计旨在引导学生设计并实现一个**面向软件项目开发的智能体系统**，使其能够在一个或多个连续开发阶段中辅助或自动完成典型软件工程任务。

**具体目标包括：**

- 理解大语言模型的基本原理及其在软件工程中的应用范式；
- 掌握智能体系统的设计方法，包括任务分解、上下文管理、工具调用等关键技术；
- 实现一个可运行的智能体原型系统，支持**需求分析、系统设计、编码实现、测试、调试、文档编写**中的至少一个连续阶段组合（详见1.2）；
- 通过系统化的测试与评估，验证智能体在基准任务上的有效性；

各小组可在上述总体目标框架下，**自主选择智能体所覆盖的具体功能范围**（最小组合见1.2），鼓励结合兴趣或实际项目背景进行创新。

---

### 1.2 技术指标与交付物

#### 1.2.1 功能要求

A. 该智能体应支持软件工程过程中**几个连续阶段**，开发团队必须明确定义其智能体的**输入形式**（如自然语言需求文档、PRD、用户故事、UML模型、代码片段、错误日志等）与**输出产物**（如设计模型、代码文件、测试用例、修复补丁、使用说明等）。可选的最小功能组合包括：

| 组合编号 | 覆盖阶段               | 具体要求                                                                 |
|----------|------------------------|--------------------------------------------------------------------------|
| a        | 分析 + 设计            | 根据系统需求或PRD，自动生成系统分析与设计模型，包括但不限于**类图、活动图、状态机图**中的至少两种，输出可采用文本描述、Mermaid/PlantUML格式等。 |
| b        | 实现 + 测试            | 根据需求、PRD或设计模型，自动生成可运行的**程序代码**（指定语言，如Python/Java）及对应的**单元测试用例**，并能执行测试并汇总结果。 |
| c        | 调试 + 程序修复        | 给定错误的程序及触发错误的测试用例，自动**定位错误位置**，解释错误原因，并生成**修复后的正确代码**。 |

> 小组也可以选择覆盖更多阶段（如分析+设计+实现）。

#### 1.2.2 非功能与集成要求

B. **命令行启动**：智能体应能够通过命令行接口（CLI）以非交互或半交互方式启动，自动完成所定义的任务，并输出结果到指定目录。例如（但不限于）：
```bash
./agent --task design --input requirements.md --output design/
```

C. **IDE集成**：智能体应能够集成到主流IDE中（如VSCode、Eclipse、IntelliJ IDEA等），至少实现以下一种集成形式：
- 作为插件或扩展，提供菜单/快捷键触发；
- 通过语言服务器协议（LSP）或自定义命令与IDE交互；
- 提供可嵌入IDE的Web服务接口。

D. **基准测试**：智能体必须通过指定的基准测试，以证明其在所选任务上的有效性。基准测试由课程组提供或小组自行构建但需经教师认可。测试内容应覆盖：
- 至少5个不同场景/案例；
- 度量并报告成功率。

#### 1.2.3 交付物清单

开发小组需要提交以下文档（均要求PDF格式，并附源代码仓库链接）：

| 编号 | 文档名称                         | 主要内容要求                                                                 |
|------|----------------------------------|------------------------------------------------------------------------------|
| a    | 智能体工作原理技术报告           | 包括大模型选择（如GPT、Claude、Llama等）、提示工程策略、任务分解与编排机制、错误处理与重试逻辑、工具调用（如代码执行、静态分析）等。 |
| b    | 智能体系统设计方案               | 系统架构图、模块划分、数据流、核心类/接口设计、关键技术选型理由。             |
| c    | 智能体系统测试方案与测试报告     | 测试环境、测试用例设计（正常/异常/边界）、基准测试结果、性能分析、局限性说明。 |
| d    | 智能体使用说明与应用案例         | 安装配置步骤、CLI命令详解、IDE集成方法、至少两个完整应用案例（从输入到输出的演示）。 |

---

### 1.3 开发约束

A. **禁止直接扩展已有软件工程智能体**：不得基于MetaGPT、ChatDev、AutoGPT等现有软件工程智能体系统的代码进行简单封装或参数调整。但允许使用**通用智能体框架**作为底层基础设施，例如：
   - **CrewAI**：用于定义角色、任务和流程编排；
   - **LangGraph** / **LangChain**：用于构建基于大模型的图式工作流；
   - **Semantic Kernel**、**DSPy** 等研究性框架。

若使用了上述框架，必须在技术报告中明确说明哪些部分为自主实现，哪些由框架提供。

B. **代码与数据开源**：所有实现的源代码、配置文件、测试数据必须提交至Git仓库（校内GitLab），仓库需包含详细的README，说明如何复现环境与运行智能体。

C. **里程碑检查点**：
   - 第1周：选题确认
   - 第3周：需求分析（明确所选功能组合、基准测试方案）与系统设计；
   - 第6周：设计方案、原型系统实现、确定测试方案；
   - 第8周：最终交付（所有文档+演示）。

# 三、 评价指标

说明：下面的评价指标对应课程的五个教学目标

+ **软件系统（40%）**：需求达成度+完成质量
  - 软件分析和设计的质量
  - 代码质量将占有分数（占5%）
  - 课程将设置一次中期检查（课程第5~6周，占10%），中期检查将直接影响最终得分
+ **开发环境（10%）**：使用现代开发环境和工具开发，包括但不限于
  - 能够熟练使用git系统进行代码管理，包括分支、提交、pull request等
  - 能够使用wiki、bug issue等功能管理项目开发
  - 能够使用代码分析、自动化编译和测试功能改进开发
  - 使用Docker等工具规范开发环境
+ **团队合作（10%）**：有合理分工并且能够相互协作
  - 分工明确性
  - 协作程度
+ **文档和报告（30%）**：最终文档和演示的质量
  - 文档的格式规范性和内容的规范性（15%）
  - 演示汇报（10%)：展示软件工程全过程，重点阐述难点及解决方案
  - 技术学习（5%）：对相关技术的学习过程及收获展示
+ **过程管理（10%）**：有合理的进度安排并能充分利用时间、把握进度
  - 有开发计划和明确的里程碑（里程碑应对应需求）
  - 开发应充分利用时间
  - 能够基本按照计划完成开发

# 四、  课程安排
## 1.  组队

每个开发团队由4-6名成员组成，其中1名作为组长。

+ 组长需要负责组织和管理项目开发，协调小组成员、解决成员间的分歧。组长将在最终评分中获得组长加成（+5%~+10%）。
+ 小组成员需要服从组长安排，对于拒不服从安排的成员，经组长申请、助教核实后，在最终评分中将受到惩罚（-5%~-50%）。
+ 开发团队规模小于6人时，将有机会获得额外的加分。

## 2.  选题

每个小组在上课之前需要对所有选题进行研究，并在第一次上课时确定选题。每个小组只能选择一个题目，且不建议在进行过程中更换题目，因此请谨慎进行选题可行性分析。

每个选题包括若干需求，选题需求将有可能在课程后半段（课程第5~6周）发生一次演化。

在明确规定的需求之上，各小组可根据情况自行扩展需求，当扩展需求比原需求显著增强时，可获得额外加分。

## 3.  组长会

每次上课将组织组长会。组长会以选题为单位进行组织，所有相同选题的小组长负责参加讨论。组长会的内容如下：

+ 每个组长进行每周工作小结
+ 汇总各小组遇到的问题
+ 相互讨论，以便形成解决方案

组长会是各小组相互交流和学习的机会，也是共同商讨复杂问题的解决方案的机会。各小组应充分利用这一机会，在竞争中相互帮助。

## 4.  技术方案保护制度

为了鼓励和保障在组长会上分享解决方案和思路小组，各小组可以申请“技术方案保护”。每周定时审查一次申请。最先成功申请技术方案保护的小组可以获得技术加分。技术方案保护需要公开，并共享给所有团队。
