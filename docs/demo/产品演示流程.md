# CodeAgent 产品演示流程

本文档是一份面向课程展示和答辩的操作讲稿。它不只列命令，还解释每一步“为什么做、在展示什么功能、观众应该看哪里、输出结果应该怎么读”。

演示者可以把本文档当作现场脚本使用：先照着“演示者讲解”介绍背景，再执行“操作命令”，然后按“怎么看输出”解释结果。

## 1. 演示总目标

CodeAgent 要展示的不是一个普通脚本，而是一个本地 CLI 软件工程智能体。它的核心价值是：

- 把软件工程任务拆成 `implement -> test -> debug -> repair` 四类阶段。
- 用 LangGraph 编排阶段流转、条件路由、interrupt 和 checkpoint/resume。
- 用 LangChain/OpenRouter 调用真实 LLM 生成计划、补丁、测试、调试分析和修复建议。
- 用 patch-first 约束所有代码修改：LLM 不能直接写源文件，只能生成 unified diff，再由系统校验、审批、应用。
- 用 HITL 和 decision trace 记录副作用操作，让“谁批准了什么、执行了什么”可追踪。
- 每次运行都保存结构化产物，便于复盘、评分、debug 和答辩。
- benchmark 每个 case 都复制到干净运行目录中执行，原始 case 不被污染，可以反复使用。

演示时建议不断强调一句话：

> CodeAgent 的重点不是只给出一个答案，而是把智能体每一步工程行为都记录下来，让结果可检查、可复现、可追责。

## 2. 推荐演示路线

建议课堂展示分为 6 段：

| 段落 | 建议时间 | 现场要做什么 | 主要说明什么 |
|---|---:|---|---|
| 1. 产品入口检查 | 2 分钟 | 查看 CLI help 和环境变量 | 证明这是可运行的 CLI 产品，不只是代码库 |
| 2. 非交互示例任务 | 5 分钟 | 运行 `examples\task.yaml` | 展示配置驱动运行、阶段路由、run 产物 |
| 3. 运行产物讲解 | 6 分钟 | 打开 `final_report.md`、`artifacts_index.json`、`transcript.jsonl` | 解释产物含义，说明可审计性 |
| 4. 半交互 wizard | 4 分钟 | 运行 `codeagent wizard` | 展示用户如何创建任务、确认配置、进入可恢复运行 |
| 5. Benchmark 展示 | 8 分钟 | 展示公开和自建 benchmark 报告 | 展示真实 LLM 能力、case 隔离、oracle 评测结果 |
| 6. 总结答辩 | 5 分钟 | 结合实现汇报说明架构 | 连接到 LangGraph、LangChain、patch-first、checkpoint |

如果现场时间很短，至少展示三件事：

1. `python -m codeagent run --config examples\task.yaml`
2. 该 run 目录下的 `final_report.md` 和 `artifacts_index.json`
3. 已完成 benchmark 的 `benchmark_report.md`

这三件事能覆盖“能跑、可审计、真实评测”三个核心点。

## 3. 演示前准备

### 3.1 进入项目根目录

操作命令：

```powershell
cd D:\Projects\CodeAgent
```

演示者讲解：

> 我们现在进入 CodeAgent 项目根目录。后续所有命令都从这里执行，这样示例配置中的相对路径、benchmark 配置和输出目录都能正确解析。

怎么看输出：

- 这一步通常没有输出。
- 如果路径不存在，说明演示环境没有切到项目所在机器或项目目录。

### 3.2 安装本地包

操作命令：

```powershell
python -m pip install -e .
```

演示者讲解：

> 这一步把当前项目以 editable 模式安装到本地 Python 环境。安装后既可以用 `python -m codeagent` 运行，也可以直接用 `codeagent` 控制台命令运行。editable 模式适合课程项目，因为代码修改后不需要重新打包。

怎么看输出：

- 正常情况下 pip 会显示安装依赖和安装 `codeagent`。
- 如果已经安装过，pip 可能显示 requirement already satisfied，这是正常的。
- 如果提示 Python 版本不满足，需要使用 Python 3.11 或更高版本。

这一步展示的功能：

- CodeAgent 是一个按 Python 包组织的产品，不是散落脚本。
- `pyproject.toml` 中定义了依赖和 `codeagent` console script。

### 3.3 查看 CLI 总入口

操作命令：

```powershell
python -m codeagent --help
```

可选再执行：

```powershell
codeagent --help
```

演示者讲解：

> 这里展示 CodeAgent 的产品入口。可以看到它提供了向导模式、配置运行、四个阶段子命令、benchmark 和 resume。也就是说，用户既可以通过一个完整配置文件跑任务，也可以单独调用实现、测试、调试或修复阶段。

怎么看输出：

关注 Commands 区域，应该看到：

```text
wizard
run
implement
test
debug
repair
benchmark
resume
```

每个命令的含义：

- `wizard`：半交互创建任务配置。
- `run`：从 YAML/JSON 配置执行一个任务。
- `implement`：只执行实现阶段。
- `test`：只执行测试阶段。
- `debug`：只执行调试阶段。
- `repair`：只执行修复阶段。
- `benchmark`：运行 benchmark 套件并汇总结果。
- `resume`：查看或恢复已有运行。

这一步展示的功能：

- CLI 命令体系完整。
- 产品可以面向真实用户操作，不依赖开发者手写 Python 调用。

### 3.4 检查 OpenRouter 环境变量

操作命令：

```powershell
python -c "import os; print('OPENROUTER_API_KEY configured:', bool(os.environ.get('OPENROUTER_API_KEY')))"
```

演示者讲解：

> CodeAgent 的真实 LLM 调用通过 OpenRouter。我们只检查环境变量是否存在，不打印密钥值。这个设计是为了避免 API Key 出现在终端、文档、报告或 Git 历史里。

怎么看输出：

期望看到：

```text
OPENROUTER_API_KEY configured: True
```

如果是 `False`：

- 说明当前终端进程没有读取到环境变量。
- 可以重新打开 PowerShell，或临时设置当前进程环境变量。
- 现场不要展示真实 key。

临时设置示例：

```powershell
$env:OPENROUTER_API_KEY = "请填入你的 OpenRouter API Key"
```

这一步展示的功能：

- 真实 LLM 调用已经具备环境条件。
- Secret 只通过环境变量进入运行时，不写入配置文件和报告。

## 4. 第一段核心演示：非交互示例任务

这一段是最建议现场运行的任务，因为它稳定、快速、不会消耗 LLM token，也不会修改项目源代码。

### 4.1 先介绍 `examples\task.yaml` 是什么

打开配置文件：

```powershell
Get-Content -LiteralPath examples\task.yaml -Encoding UTF8
```

文件内容核心如下：

```yaml
schema_version: 1
task_id: example-debug-static-log
title: Static log debugging example
stages:
  - debug
project_path: debug_project
output_dir: ../codeagent_runs/examples
language: python
test_framework: pytest
input_materials:
  - material_type: error_log
    path: debug_project/failing.log
    required: true
    multi: true
    description: Public failure log used by the debug-only example.
test_command:
  command: "pytest -q"
  timeout_seconds: 10
```

演示者讲解：

> 这个配置描述了一个很小的调试任务。它的任务 id 是 `example-debug-static-log`，标题是“静态日志调试示例”。`stages` 里只有 `debug`，表示这次不做实现、不写测试、不修代码，只演示调试阶段。`project_path` 指向 `examples/debug_project`，输入材料是 `debug_project/failing.log`，也就是一段公开的 pytest 失败日志。输出会写到 `codeagent_runs/examples`。

逐项解释：

- `schema_version`：配置文件版本，便于以后演进。
- `task_id`：任务标识，进入 metadata 和报告。
- `stages: debug`：只执行调试阶段，用来演示阶段路由和报告生成。
- `project_path: debug_project`：被分析的示例项目目录。
- `output_dir`：运行产物输出到项目根目录下的 `codeagent_runs/examples`。
- `input_materials`：给智能体看的输入材料，这里是一份失败日志。
- `test_command`：任务的测试命令。这个示例不会真正跑测试，但配置中仍保留命令，展示 TaskConfig 的统一结构。

为什么现在要运行这个任务：

- 它足够小，现场 10 秒左右就能跑完。
- 它不会调用真实 LLM，不会消耗 OpenRouter token。
- 它不会生成 patch，不会改源码。
- 它能展示 CodeAgent 的配置加载、阶段选择、LangGraph 路由、run directory、报告系统、artifact index 和 transcript。

这个任务不展示什么：

- 它不展示真实 LLM 生成代码。
- 它不展示 patch-first 应用补丁。
- 它不展示 oracle benchmark。

因此后面还要展示 benchmark 报告，补足真实 LLM 和评测能力。

### 4.2 查看示例输入日志

操作命令：

```powershell
Get-Content -LiteralPath examples\debug_project\failing.log -Encoding UTF8
```

期望输出：

```text
FAILED tests/test_calculator.py::test_add - AssertionError
E assert 0 == 2
1 failed, 3 passed in 0.05s
```

演示者讲解：

> 这是调试阶段要读取的公开失败日志。日志告诉我们 `tests/test_calculator.py::test_add` 失败了，断言里实际值是 0，期望值是 2。这个示例项目很小，重点不是修复这个 bug，而是展示 CodeAgent 如何把失败日志转成调试产物，例如 failure summary、fault localization、root cause 和 repair plan。

怎么看输出：

- `FAILED ... test_add`：失败测试名称。
- `AssertionError`：失败类型。
- `E assert 0 == 2`：实际值和期望值的差异。
- `1 failed, 3 passed`：测试总体结果。

这一步展示的功能：

- CodeAgent 可以把外部日志作为输入材料。
- 调试阶段不一定要现场复现失败，也可以基于已有失败日志工作。

### 4.3 运行示例任务

操作命令：

```powershell
python -m codeagent run --config examples\task.yaml
```

演示者讲解：

> 现在运行这个配置文件。`run` 命令会读取 YAML，校验阶段和路径，创建 run directory，然后把任务交给 LangGraph 主工作流。因为配置里只有 `debug` 阶段，主图会从入口直接路由到 debugging 子图，运行完成后写最终报告。

期望看到类似输出：

```text
[stage] route_entry completed
[route] entry -> debugging: start selected stage debug
[stage] debugging completed
[result] debugging succeeded: Debugging completed with low confidence and no concrete source candidate.
[stage] route_after_debugging completed
[route] debugging -> final_success: debugging succeeded
[stage] final_success completed
[final] succeeded
Run directory: D:/Projects/CodeAgent/codeagent_runs/examples/<run_id>
Final status: succeeded
```

逐行解释：

- `[stage] route_entry completed`：主图入口路由节点执行完成。
- `[route] entry -> debugging`：因为配置只选择了 debug 阶段，所以路由进入 debugging。
- `[stage] debugging completed`：debugging 子图或阶段 handler 完成。
- `[result] debugging succeeded ...`：调试阶段产出了一个成功的阶段结果。
- `low confidence and no concrete source candidate`：因为示例只提供静态失败日志，没有完整源码和真实复现上下文，所以系统低置信地给出分析，不伪装成已经定位到明确源码。
- `[route] debugging -> final_success`：debug 阶段成功后进入最终成功节点。
- `[final] succeeded`：整个 run 成功结束。
- `Run directory`：本次运行的所有产物都在这个目录。
- `Final status`：最终状态，成功时为 `succeeded`。

这一步展示的功能：

- 配置驱动运行。
- LangGraph 主图按阶段选择进行路由。
- 阶段结果会进入最终状态判断。
- 系统会给出 run directory，所有证据都落盘保存。

答辩时可以这样解释：

> 这里我们不是手动调用某个函数，而是通过统一 CLI 和 YAML 配置启动完整运行框架。即使这个任务只跑 debug，它也走了 CodeAgent 的标准 run context、图路由、报告和 artifact 记录流程。

## 5. 第二段核心演示：读懂运行产物

这段非常重要。很多答辩只展示“命令成功了”，但 CodeAgent 的重点是“成功背后有什么证据”。所以要打开 run directory 解释每个文件。

### 5.1 找到刚才的 run directory

如果终端还显示 `Run directory`，直接复制它。

如果需要自动找最新一次示例运行：

```powershell
$run = Get-ChildItem -LiteralPath codeagent_runs\examples -Directory | Sort-Object LastWriteTime -Descending | Select-Object -First 1
$run.FullName
```

演示者讲解：

> 每次运行都会生成一个唯一目录。目录名里包含时间戳、阶段和短 hash，例如 `2026-06-03_112448_512998_debug_6fd311`。这样多次运行不会覆盖，也方便回溯。

怎么看输出：

- 输出应该是一个完整路径，例如：

```text
D:\Projects\CodeAgent\codeagent_runs\examples\2026-06-03_112448_512998_debug_6fd311
```

这一步展示的功能：

- run_id 唯一。
- 运行产物隔离保存。
- 后续 resume 和报告索引都基于这个 run_id。

### 5.2 查看 run 目录结构

操作命令：

```powershell
Get-ChildItem -LiteralPath $run.FullName
```

期望看到：

```text
benchmark/
debugging/
implementation/
repair/
testing/
artifacts_index.json
checkpoints.sqlite
decision_trace.jsonl
final_report.md
metadata.json
task_config.yaml
transcript.jsonl
```

演示者讲解：

> 这里可以看到 CodeAgent 的标准运行目录。即使这次只执行 debug，系统仍创建了完整的阶段目录。这么做是为了让所有 run 的结构一致，后续无论是单阶段还是多阶段，都能用同一套报告、resume 和 benchmark 工具读取。

逐项解释：

- `metadata.json`：本次运行的基础信息，例如 run_id、创建时间、任务 id、模型配置摘要。
- `task_config.yaml`：归一化后的任务配置。它是复现实验的重要依据。
- `transcript.jsonl`：运行过程中发生的阶段事件，一行一个 JSON。
- `decision_trace.jsonl`：审批和副作用决策记录。这个示例没有审批，所以可能为空。
- `artifacts_index.json`：所有产物的索引，说明每个产物是什么、属于哪个阶段、路径在哪里。
- `checkpoints.sqlite`：LangGraph checkpoint 数据库，用于 resume。
- `final_report.md`：最终总结报告，适合给人阅读。
- `debugging/`：debug 阶段的详细产物。
- `implementation/`、`testing/`、`repair/`：其他阶段目录，本次未执行但目录存在。
- `benchmark/`：benchmark 相关产物目录，普通 run 通常为空。

这一步展示的功能：

- 可审计运行目录。
- 可复现配置。
- checkpoint/resume 基础设施。
- 统一 artifact 管理。

### 5.3 打开最终报告 `final_report.md`

操作命令：

```powershell
Get-Content -LiteralPath (Join-Path $run.FullName 'final_report.md') -Encoding UTF8
```

期望看到类似内容：

```markdown
# 智能体运行总结报告

## 阶段结果总览

| 阶段 | 状态 | 关键产物 | 说明 |
|---|---|---|---|
| debugging | succeeded | debugging_reproduction_report, ... | Debugging completed with low confidence and no concrete source candidate. |

## 输出产物索引

| artifact_id | stage | kind | path | summary |
...

## 审计记录

- decision_trace 事件数: 0
- transcript 事件数: 1
```

演示者讲解：

> `final_report.md` 是给人看的总报告。它不是凭空总结，而是从阶段结果和 artifact index 中生成。第一张表告诉我们哪个阶段跑了、状态是什么、关键产物有哪些；第二张表列出所有产物路径；最后的审计记录说明这次运行产生了多少决策事件和过程事件。

怎么看阶段结果总览：

- `阶段 = debugging`：说明本次只执行了 debug 阶段。
- `状态 = succeeded`：说明 debug 阶段正常完成。
- `关键产物`：列出 debugging 阶段生成的报告和 JSON。
- `说明` 中的 `low confidence`：不是失败，而是诚实表达置信度。因为只有静态失败日志，没有完整复现和源码候选，所以系统不冒充高置信定位。

怎么看输出产物索引：

- `artifact_id` 是产物唯一标识。
- `stage` 说明产物属于哪个阶段。
- `kind` 说明产物类型：report、json、log 等。
- `path` 是相对 run directory 的路径。
- `summary` 是简短说明。

怎么看审计记录：

- `decision_trace 事件数: 0`：这次没有审批动作，因为任务没有修改文件和执行需审批的副作用。
- `transcript 事件数: 1`：至少记录了 debugging 阶段结果事件。

这一步展示的功能：

- 最终报告可读。
- 报告可以追溯到结构化产物。
- 系统不会夸大静态日志分析能力，会在报告中保留置信度。

### 5.4 打开产物索引 `artifacts_index.json`

操作命令：

```powershell
Get-Content -LiteralPath (Join-Path $run.FullName 'artifacts_index.json') -Encoding UTF8
```

演示者讲解：

> `artifacts_index.json` 是机器可读的产物目录。`final_report.md` 是给人看的，`artifacts_index.json` 是给程序、评分脚本或后续 resume/分析工具看的。它让每个报告和日志都有稳定 ID，而不是靠人肉在目录里找文件。

重点字段解释：

```json
{
  "artifact_id": "debugging_failure_summary",
  "stage": "debugging",
  "kind": "report",
  "path": "debugging/failure_summary.md",
  "summary": "Debugging failure summary"
}
```

- `artifact_id`：后续报告引用这个 ID。
- `stage`：产物归属阶段。
- `kind`：产物类型。
- `path`：文件位置。
- `summary`：产物用途说明。

现场可以重点指出这些产物：

- `debugging_reproduction_report`：复现信息或静态日志说明。
- `debugging_failure_summary`：对失败日志的摘要。
- `debugging_fault_localization`：疑似故障位置，JSON 格式。
- `debugging_root_cause`：根因分析。
- `debugging_repair_plan`：给 repair 阶段使用的修复计划。
- `debugging_debug_trace`：调试过程日志。
- `debugging_debug_report`：debug 阶段完整报告。
- `debugging_stage_result`：阶段状态结构化 JSON。
- `final_report`：最终总结报告。

这一步展示的功能：

- artifact 统一登记。
- 报告可机器读取。
- 后续 benchmark、resume、评分系统可以直接消费这些产物。

### 5.5 打开 transcript

操作命令：

```powershell
Get-Content -LiteralPath (Join-Path $run.FullName 'transcript.jsonl') -Encoding UTF8
```

期望看到类似内容：

```json
{"type":"stage_result","stage":"debugging","status":"succeeded",...}
{"type":"final_report","path":"final_report.md","stage_count":1,...}
```

演示者讲解：

> `transcript.jsonl` 是运行过程流水账。JSONL 的意思是一行一个 JSON 对象，适合追加写入，也适合后续程序分析。它记录“发生了什么”，比如哪个阶段完成了、最终报告什么时候写入。

怎么看输出：

- `type=stage_result`：一个阶段产生了结果。
- `stage=debugging`：阶段名称。
- `status=succeeded`：阶段状态。
- `artifact_ids`：这个阶段登记了哪些产物。
- `type=final_report`：最终报告已写入。

这一步展示的功能：

- 运行过程可追踪。
- 不是只看终端输出，过程事件也落盘。

### 5.6 打开 decision trace

## 7. 第四段核心演示：Benchmark 与真实 LLM 能力

前面的 `examples\task.yaml` 主要展示运行框架和产物系统。要展示真实 LLM 编排、patch-first 修改、隐藏 oracle 隔离和成功率，需要看 benchmark。

完整 benchmark 可能消耗 token，也依赖网络和 OpenRouter 余额。课堂现场建议优先展示已经生成的 benchmark 报告；如果时间和网络允许，再现场运行。

### 7.1 先解释 benchmark 在测什么

演示者讲解：

> Benchmark 的目的不是让模型看答案，而是模拟真实软件工程任务。每个 case 有可见输入，比如需求、bug 报告、公开失败日志和初始代码；也有对智能体隐藏的 oracle 测试。CodeAgent 运行时只能看到 visible paths，不能看到 `oracle_tests`、`evaluation` 或 `expected_result.json`。最后由 runner 在隔离环境中执行 oracle，判断结果是否正确。

CodeAgent benchmark 的关键机制：

- 每个 case 先复制到干净 run workspace。
- 智能体只修改复制后的 workspace。
- 原始 case 保持不变，可重复使用。
- auto-approval 会写入 decision trace。
- 汇总报告包含 success rate、失败原因、blocker 和 source_unchanged。

答辩时可以这样讲：

> 这解决了两个问题：第一，智能体不会污染原始 benchmark；第二，智能体看不到隐藏答案，只能根据公开需求完成任务。

## 9. 常见输出怎么解释

### 9.1 `Final status: succeeded`

含义：

- 整个 run 的最终状态为成功。
- 不等于“所有可能功能都被测试过”，只表示本次配置选择的阶段按系统规则完成。

答辩解释：

> CodeAgent 的成功定义是配置驱动的。比如 debug-only 示例只要求 debug 阶段成功；benchmark case 则要求 agent run 和 oracle 评测都满足条件。

### 9.2 `low confidence`

含义：

- 系统完成了分析，但输入不足以高置信定位。
- 这是预期行为，不是失败。

答辩解释：

> 静态失败日志示例没有完整源码和复现上下文，所以系统不能假装确定根因。这体现了错误处理和报告的保守性。

### 9.3 `decision_trace` 为空

含义：

- 本次没有发生需要审批的副作用。
- 例如 debug-only 示例没有 patch、没有 shell approval。

答辩解释：

> 空 decision trace 不是缺失，而是说明本次运行没有修改文件或执行需要审批的命令。benchmark 或 patch 任务会产生审批记录。

### 9.4 `source_unchanged=True`

含义：

- benchmark 原始 case 未被修改。
- 智能体修改的是复制后的 case workspace。

答辩解释：

> 这是 benchmark 可重复利用的关键证据。每次评测都从干净复制开始，不会因为上一次运行污染原始样例。

### 9.5 `oracle_success=True`

含义：

- 隐藏 oracle 测试通过。
- 智能体没有看到 oracle 测试内容。

答辩解释：

> 这说明结果通过了独立评测，不只是公开测试通过。隐藏 oracle 对智能体不可见，保证评测公平。

### 9.6 `blocked=1`

含义：

- 有 case 因外部环境不满足而没有运行。
- 当前主要是 BugsInPy 需要 WSL、conda 和 Python 3.8.3。

答辩解释：

> blocker 是显式记录的环境限制，不是失败被隐藏。这样评测报告更诚实。

## 10. 演示时可以直接使用的讲稿

### 开场

> 我们做的是一个本地 CLI 软件工程智能体 CodeAgent。它围绕实现、测试、调试、修复四个阶段组织工作，用 LangGraph 管工作流，用 LangChain 调真实 LLM。和普通 demo 不同，我们重点展示它的工程化边界：patch-first、HITL、checkpoint/resume、日志报告和 benchmark 隔离。

### 运行 `examples\task.yaml` 前

> 接下来我先跑一个小型非交互示例。这个示例叫静态日志调试，不消耗 LLM token，也不会改源码。它的作用是快速展示 CodeAgent 的配置加载、阶段路由和产物体系。后面我会再展示 benchmark 来证明真实 LLM 和隐藏 oracle 评测。

### 运行完成后

> 终端里可以看到 LangGraph 从 entry 路由到 debugging，再进入 final_success。这里的 run directory 是本次运行所有证据的根目录。我们不只看成功状态，还要打开里面的报告和索引。

### 看 `final_report.md`

> 最终报告显示本次只有 debugging 阶段，状态 succeeded。关键产物列出了失败摘要、故障定位、根因分析、修复计划等。这里写了 low confidence，是因为输入只有静态日志，系统不会夸大成高置信源码定位。

### 看 `artifacts_index.json`

> 这个文件是机器可读产物索引。每个报告和日志都有 artifact id、所属阶段、类型、路径和摘要。后续 final report、resume、benchmark 分析都可以依赖这个索引，而不是靠人工猜文件。

### 看 benchmark 报告

> benchmark 展示真实 LLM 工程能力。每个 case 都先复制到干净 workspace，智能体看不到隐藏 oracle，只能基于公开输入完成任务。报告里的 `source_unchanged=True` 说明原始 case 没被污染，`oracle_success=True` 说明隐藏评测通过。

### 收尾

> 所以 CodeAgent 的完成度体现在两个层面：一是功能上能跑 CLI、阶段图、LLM、benchmark；二是工程上每一步都有配置、日志、审批、checkpoint 和报告支撑。

## 11. 演示注意事项

- 不要展示 OpenRouter API Key 的真实值。
- 现场运行完整 benchmark 前，确认网络、余额和时间。
- 如果网络不稳，优先现场跑 `examples\task.yaml`，再展示已生成 benchmark 报告。
- `examples\task.yaml` 不展示真实 LLM 代码生成，这一点要主动说明。
- benchmark 报告中的 BugsInPy blocker 是环境门控，不是普通失败。
- 展示 run 目录时，优先讲 `final_report.md`、`artifacts_index.json`、`transcript.jsonl`、`decision_trace.jsonl`。
- `codeagent_runs/` 是运行产物目录，已被 Git 忽略，不需要提交。
- 如果时间允许，打开一个 benchmark case 的 `run_dir`，展示它也有独立 final report 和 artifact index。
