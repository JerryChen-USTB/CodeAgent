# CodeAgent 产品演示流程

本文档是一份面向课程展示和答辩的演示手册。它只安排两个使用案例：

1. 非交互式案例：运行自建 benchmark，让 CodeAgent 在真实 LLM 调用下从空目录生成软件项目，并用隐藏 oracle 验证结果。演示重点软件是 `05_meeting_room_booking` 会议室预约 API。
2. 半交互式案例：使用 `codeagent wizard` 引导创建一个真实任务，再用生成的配置驱动 Agent 生成待办事项 CLI 软件。

这两个案例覆盖同一套产品能力：OpenRouter 真实 LLM 调用、LangGraph 阶段编排、LangChain 工具调用、patch-first 代码写入、测试与修复闭环、运行产物审计、benchmark 隔离复制、隐藏评测、最终软件体验。

## 1. 展示前先说清楚：CodeAgent 是什么

建议开场用下面这段话：

> CodeAgent 是一个本地 CLI 软件工程智能体。用户给它需求、设计或失败日志，它通过 LangGraph 编排 `implementation -> testing -> debugging -> repair` 阶段，通过 LangChain/OpenRouter 调用真实 LLM 生成实现计划和 patch，通过本地工具应用补丁、运行测试、记录日志，并把每次运行的证据都落盘。它不是单次问答工具，而是一个可复现、可审计、可做 benchmark 评测的软件工程 Agent。

答辩时要强调三件事：

- 它真正调用 LLM：默认模型为 `anthropic/claude-sonnet-4.6`，API Key 来自 `OPENROUTER_API_KEY` 环境变量。
- 它真正生成软件：自建 benchmark 的 workspace 初始为空，Agent 需要创建包、模块、依赖文件、接口逻辑和持久化逻辑。
- 它真正接受评测：benchmark runner 会把 case 复制到干净运行目录，Agent 只能看到公开输入，隐藏 oracle 只由评测器执行，原始 case 不会被污染。

## 2. 展示前准备

### 2.1 进入项目根目录

操作命令：

```powershell
cd D:\Projects\CodeAgent
```

这一步在做什么：

进入 CodeAgent 项目根目录。后续所有命令都从这里执行，避免相对路径解析到错误位置。

期望看到什么：

通常没有输出。如果 PowerShell 提示路径不存在，说明当前机器上项目位置不对，需要先切到实际仓库目录。

### 2.2 安装本地包

操作命令：

```powershell
python -m pip install -e .
```

这一步在做什么：

把当前仓库以 editable 模式安装到当前 Python 环境，使 `python -m codeagent` 和 `codeagent` 命令可以直接使用。

期望看到什么：

看到 pip 安装依赖和安装 `codeagent`。如果显示 `Requirement already satisfied` 或已经安装，也是正常结果。

### 2.3 检查 CLI 入口

操作命令：

```powershell
python -m codeagent --help
```

这一步在展示什么：

展示 CodeAgent 是一个完整 CLI 产品，不是只能由开发者手动调用 Python 函数。输出中应该能看到这些命令：

```text
wizard
run
implement
test
debug
repair
benchmark
resume
```

怎么解释：

- `wizard`：半交互式创建任务配置。
- `run`：从 YAML/JSON 配置运行完整任务。
- `implement/test/debug/repair`：单独运行某个阶段。
- `benchmark`：运行 benchmark 套件并汇总评分。
- `resume`：检查或恢复已有 run。

### 2.4 检查 OpenRouter 环境变量

操作命令：

```powershell
python -c "import os; print('OPENROUTER_API_KEY configured:', bool(os.environ.get('OPENROUTER_API_KEY')))"
```

这一步在做什么：

只检查环境变量是否存在，不打印 API Key 内容。这样能证明现场具备真实 LLM 调用条件，同时避免密钥进入终端截图、报告或 Git 历史。

期望输出：

```text
OPENROUTER_API_KEY configured: True
```

怎么解释：

如果是 `True`，说明后续 Agent 可以通过 OpenRouter 调用模型。如果是 `False`，当前终端进程没有读取到环境变量，需要重新打开终端或重新设置用户级环境变量。展示现场不要把真实 key 打出来。

## 3. 非交互式使用案例：自建 benchmark 生成完整软件

这是本次演示的第一条主线，也是最能证明产品能力的一条主线。它不是跑一个玩具配置，而是运行课程自建 benchmark，让 Agent 从空 workspace 生成多个软件项目，并由隐藏 oracle 评测。

### 3.1 先介绍这个 benchmark 是什么

打开 benchmark 总配置：

```powershell
Get-Content -LiteralPath benchmark\selfbuilt\selfbuilt_benchmark.yaml -Encoding UTF8
```

你需要向观众解释：

`benchmark\selfbuilt\selfbuilt_benchmark.yaml` 是自建 benchmark 套件配置。它定义了 5 个课程场景：

| case | 类型 | 难度 | Agent 需要生成什么 |
|---|---|---|---|
| `01_todo_manager` | CLI | introductory | 待办事项管理工具，JSON 持久化 |
| `02_personal_ledger` | CLI | easy | 个人记账工具，JSON/CSV |
| `03_student_gradebook` | CLI | medium | 学生成绩管理工具，CSV 导入导出 |
| `04_library_lending` | CLI | medium_high | 图书借阅系统，SQLite |
| `05_meeting_room_booking` | Flask API | high | 会议室预约 API，SQLite |

为什么要用它演示：

- 每个 case 的 `workspace/` 初始为空，Agent 必须自己创建项目结构和业务代码。
- Agent 可见的是 `input/` 和 `workspace/`，不可见的是 `oracle_tests/`。
- runner 会把原始 case 复制到本次 benchmark 的 `case_workspaces/`，Agent 只修改副本。
- 运行结束后报告里有 `oracle_success` 和 `source_unchanged`，可以证明隐藏评测通过且原始 case 没被污染。

### 3.2 重点介绍本次要体验的软件：会议室预约 API

查看公开需求：

```powershell
Get-Content -LiteralPath benchmark\selfbuilt\cases\05_meeting_room_booking\input\requirements.md -Encoding UTF8
```

这一步在展示什么：

向观众说明 Agent 接收的是自然语言需求，而不是预先写好的代码。`05_meeting_room_booking` 要求 Agent 从空 `workspace/` 生成一个 Flask API，核心功能包括：

- `GET /health` 健康检查。
- `POST /rooms` 创建会议室。
- `GET /rooms` 查看会议室。
- `POST /bookings` 创建预约。
- `GET /bookings?date=...&room_id=...` 查询预约。
- `DELETE /bookings/<id>` 取消预约。
- 使用 SQLite 持久化。
- 处理时间格式、预约冲突、重复会议室、非法参数等边界情况。

再查看验收标准：

```powershell
Get-Content -LiteralPath benchmark\selfbuilt\cases\05_meeting_room_booking\input\acceptance_criteria.md -Encoding UTF8
```

怎么解释：

验收标准说明这个任务不是只要求“能启动”，而是要满足 API 契约、错误状态码、冲突检测、取消后释放时间段等行为。隐藏 oracle 会根据这些行为评测生成的软件。

### 3.3 运行自建 benchmark

操作命令：

```powershell
python -m codeagent benchmark --config benchmark\selfbuilt\selfbuilt_benchmark.yaml
```

这一步在做什么：

启动非交互式 benchmark。CodeAgent 会按配置依次执行 5 个 case。对每个 case，runner 会：

1. 创建本次 benchmark 的唯一输出目录。
2. 把原始 case 复制到 `case_workspaces/<case_id>`。
3. 把 Agent 可见路径限制在公开输入和 workspace。
4. 调用真实 LLM 生成实现计划和 patch。
5. 应用 patch 并运行阶段测试。
6. 由 benchmark evaluator 执行隐藏 oracle。
7. 写入聚合报告和每个 case 的运行产物。

终端上期望看到什么：

你会看到阶段流转输出，例如：

```text
[stage] route_entry completed
[route] entry -> implementation: start selected stage implementation
[stage] implementation completed
[stage] testing completed
[route] testing -> final_success: testing succeeded
Benchmark completed: success_rate=1.00 (5/5) blocked=0
Benchmark directory: D:/Projects/CodeAgent/benchmark/selfbuilt/codeagent_runs/benchmark/<benchmark_run_id>
```

怎么解释：

- `[route]` 行说明 LangGraph 正在按状态路由到不同阶段。
- `implementation completed` 说明 Agent 已生成并应用实现 patch。
- `testing completed` 说明本地测试阶段完成。
- `success_rate=1.00 (5/5)` 说明 5 个自建 case 全部通过最终评测。
- `blocked=0` 说明没有因为环境缺失而阻塞。
- `Benchmark directory` 是本次演示最重要的证据目录。

注意：

这一步会消耗 OpenRouter token。正式答辩可以现场运行，也可以在答辩前运行一次，现场打开同一个命令生成的最新报告讲解。无论哪种方式，讲解时都要明确说明这条命令是真实 benchmark 入口。

### 3.4 找到最新 benchmark 输出目录

操作命令：

```powershell
$bench = Get-ChildItem -LiteralPath benchmark\selfbuilt\codeagent_runs\benchmark -Directory |
  Sort-Object LastWriteTime -Descending |
  Select-Object -First 1
$bench.FullName
```

这一步在做什么：

把最新一次自建 benchmark 的输出目录保存到 `$bench` 变量，后续都基于这个目录查看报告、case 副本和生成的软件。

期望看到什么：

类似：

```text
D:\Projects\CodeAgent\benchmark\selfbuilt\codeagent_runs\benchmark\2026-06-03_100356_416230_codeagent_selfbuilt_python_benchmark_670ea1
```

### 3.5 阅读 benchmark 聚合报告

操作命令：

```powershell
Get-Content -LiteralPath (Join-Path $bench.FullName "benchmark_report.md") -Encoding UTF8
```

这一步在展示什么：

展示整套 benchmark 的最终成绩。报告里应该能看到：

```text
Total cases: 5
Success cases: 5
Failed cases: 0
Blocked cases: 0
Success rate: 1.00
```

表格里重点看这些列：

- `case_id`：每个评测任务。
- `success`：该 case 是否最终成功。
- `final_status`：Agent 自身工作流是否成功结束。
- `oracle_success`：隐藏 oracle 是否通过。
- `source_unchanged`：原始 benchmark case 是否保持不变。
- `score`：该 case 得分。
- `run_dir`：该 case 的 Agent 运行产物目录。

推荐现场讲解词：

> 这里的成功不是 Agent 自己说成功，而是 benchmark runner 对每个 case 运行隐藏 oracle 后给出的结果。`oracle_success=True` 说明生成的软件通过了隐藏验收；`source_unchanged=True` 说明 runner 没有污染原始 case，而是在干净副本中执行。

### 3.6 用 JSON 结果精确核对每个 case

操作命令：

```powershell
$result = Get-Content -LiteralPath (Join-Path $bench.FullName "benchmark_result.json") -Encoding UTF8 -Raw | ConvertFrom-Json
$result.cases | Format-Table case_id, success, oracle_success, source_unchanged, score
```

期望看到什么：

```text
case_id                 success oracle_success source_unchanged score
-------                 ------- -------------- ---------------- -----
01_todo_manager            True           True             True  1.0
02_personal_ledger         True           True             True  1.0
03_student_gradebook       True           True             True  1.0
04_library_lending         True           True             True  1.0
05_meeting_room_booking    True           True             True  1.0
```

怎么解释：

这一步把 Markdown 报告中的结论换成结构化数据展示。答辩时可以说：报告既给人读，也给机器读；后续可以接入课程评分脚本或 CI。

### 3.7 进入会议室预约 API 的生成目录

操作命令：

```powershell
$meetingCase = Join-Path $bench.FullName "case_workspaces\05_meeting_room_booking"
$meetingWorkspace = Join-Path $meetingCase "workspace"
Get-ChildItem -LiteralPath $meetingWorkspace -Recurse -File |
  Where-Object { $_.FullName -notmatch "__pycache__" } |
  Select-Object FullName
```

这一步在展示什么：

展示 Agent 真的从空 workspace 生成了软件产物。你应该能看到类似文件：

```text
workspace\requirements.txt
workspace\meeting_room_booking\__init__.py
workspace\meeting_room_booking\app.py
workspace\meeting_room_booking\repository.py
workspace\meeting_room_booking\service.py
```

怎么解释：

- `requirements.txt` 是 Agent 按需求创建的 Flask 依赖声明。
- `meeting_room_booking\__init__.py` 暴露 `create_app`。
- `app.py` 定义 Flask 路由和 HTTP 响应。
- `repository.py` 负责 SQLite 表结构和数据访问。
- `service.py` 负责业务规则，例如时间校验和冲突检测。

这一步证明：benchmark 不是只评估单个函数，而是要求 Agent 生成一个有模块结构、有依赖、有持久化、有业务规则的软件项目。

### 3.8 查看该 case 的 Agent 运行报告

操作命令：

```powershell
$caseResult = $result.cases | Where-Object { $_.case_id -eq "05_meeting_room_booking" }
$caseRun = $caseResult.run_dir
Get-Content -LiteralPath (Join-Path $caseRun "final_report.md") -Encoding UTF8
```

这一步在展示什么：

展示 CodeAgent 自身工作流的运行产物。`final_report.md` 通常包含：

- 阶段结果总览。
- implementation/test/debug/repair 各阶段状态。
- 输出产物索引。
- decision trace 事件数。
- transcript 事件数。

怎么解释：

单个 case 的 `final_report.md` 是 Agent 自己的审计报告，说明它生成了哪些 patch、跑了哪些阶段、记录了哪些日志。隐藏 oracle 的最终评测结果在 benchmark 聚合报告和 `benchmark_result.json` 中体现。两者是互补关系：

- Agent 报告回答“它怎么做的”。
- Benchmark 报告回答“做得是否满足隐藏验收”。

### 3.9 查看 patch-first 产物

操作命令：

```powershell
Get-Content -LiteralPath (Join-Path $caseRun "implementation\changed_files.json") -Encoding UTF8
Get-Content -LiteralPath (Join-Path $caseRun "implementation\implementation.patch.diff") -Encoding UTF8 -TotalCount 120
```

这一步在展示什么：

展示 CodeAgent 不让 LLM 直接随意写文件，而是要求 LLM 生成 unified diff，由系统校验、应用、记录。

怎么解释：

- `changed_files.json` 说明本次实现修改或新增了哪些文件。
- `implementation.patch.diff` 是实际应用到 workspace 的补丁。
- patch-first 的价值是可审计、可回滚、可做风险检查，也方便答辩时解释“代码从哪里来”。

### 3.10 查看隐藏 oracle 结果，但不打开隐藏测试源码

操作命令：

```powershell
$caseResult | Select-Object case_id, oracle_success, oracle_command, oracle_logs_dir
Get-ChildItem -LiteralPath $caseResult.oracle_logs_dir -File | Select-Object Name, Length
```

这一步在展示什么：

展示隐藏评测确实执行过，但不泄漏隐藏测试内容。你应该看到：

```text
oracle_success : True
oracle_command : python -m unittest discover -s oracle_tests
```

怎么解释：

`oracle_tests` 对 Agent 不可见，只由 benchmark evaluator 执行。我们现场只读评测结果和日志文件名，不打开 oracle 源码。这符合 benchmark 的公平性设计。

### 3.11 实际体验 Agent 生成的会议室预约 API

这一段非常重要。前面证明“Agent 生成并通过评测”，这里证明“生成的软件可以被人实际使用”。

先进入生成的软件目录：

```powershell
Push-Location $meetingWorkspace
```

安装生成项目的依赖：

```powershell
python -m pip install -r requirements.txt
```

先确认 Flask 能加载 Agent 生成的应用，并列出路由：

```powershell
$env:PYTHONPATH = (Get-Location).Path
python -m flask --app "meeting_room_booking:create_app" routes
```

期望看到：

```text
Endpoint        Methods  Rule
--------------  -------  --------------------------
cancel_booking  DELETE   /bookings/<int:booking_id>
create_booking  POST     /bookings
create_room     POST     /rooms
health          GET      /health
list_bookings   GET      /bookings
list_rooms      GET      /rooms
```

怎么解释：

这一步在启动服务前先做一次快速检查：Flask 能导入 `meeting_room_booking:create_app`，并且生成的软件暴露了需求中要求的接口。

启动 Flask API：

```powershell
python -m flask --app "meeting_room_booking:create_app" run --host 127.0.0.1 --port 5055
```

这一步在做什么：

把 Agent 生成的 Flask 应用作为真实 HTTP 服务启动。这个命令会占用当前终端。后面的 API 调用需要在第二个 PowerShell 窗口中执行。

期望看到什么：

```text
* Serving Flask app 'meeting_room_booking:create_app'
* Running on http://127.0.0.1:5055
```

在第二个 PowerShell 窗口中执行健康检查：

```powershell
curl.exe -i http://127.0.0.1:5055/health
```

期望看到：

```text
HTTP/1.1 200 OK
{"status":"ok"}
```

怎么解释：

这说明 Flask 应用已启动，`create_app` 工厂函数可被加载，基础路由工作正常。

创建会议室：

```powershell
curl.exe -i -X POST http://127.0.0.1:5055/rooms `
  -H "Content-Type: application/json" `
  -d '{"name":"Room A","capacity":8,"location":"2F"}'
```

期望看到：

```text
HTTP/1.1 201 CREATED
{"capacity":8,"id":1,"location":"2F","name":"Room A"}
```

怎么解释：

这展示了输入校验、SQLite 写入、JSON 响应和自增 ID。

查看会议室列表：

```powershell
curl.exe -i http://127.0.0.1:5055/rooms
```

期望看到：

```text
HTTP/1.1 200 OK
[{"capacity":8,"id":1,"location":"2F","name":"Room A"}]
```

创建一个预约：

```powershell
curl.exe -i -X POST http://127.0.0.1:5055/bookings `
  -H "Content-Type: application/json" `
  -d '{"room_id":1,"user":"Ada","title":"Weekly Sync","start":"2026-06-10 09:00","end":"2026-06-10 10:00"}'
```

期望看到：

```text
HTTP/1.1 201 CREATED
{"end":"2026-06-10 10:00","id":1,"room_id":1,"start":"2026-06-10 09:00","status":"active","title":"Weekly Sync","user":"Ada"}
```

怎么解释：

这展示了预约创建、时间格式解析、默认 active 状态和数据库持久化。

制造一个冲突预约：

```powershell
curl.exe -i -X POST http://127.0.0.1:5055/bookings `
  -H "Content-Type: application/json" `
  -d '{"room_id":1,"user":"Grace","title":"Conflict Meeting","start":"2026-06-10 09:30","end":"2026-06-10 10:30"}'
```

期望看到：

```text
HTTP/1.1 409 CONFLICT
{"error":"booking conflict"}
```

怎么解释：

这是业务规则演示的重点。同一会议室中，`09:30-10:30` 与已有 `09:00-10:00` 重叠，所以系统拒绝预约并返回 409。这证明生成的软件不是只实现 CRUD，还实现了需求中的核心规则。

创建边界相接的预约：

```powershell
curl.exe -i -X POST http://127.0.0.1:5055/bookings `
  -H "Content-Type: application/json" `
  -d '{"room_id":1,"user":"Linus","title":"Next Meeting","start":"2026-06-10 10:00","end":"2026-06-10 11:00"}'
```

期望看到：

```text
HTTP/1.1 201 CREATED
```

怎么解释：

需求规定边界相接不算冲突，`10:00-11:00` 可以接在 `09:00-10:00` 后面。这证明 Agent 生成的逻辑理解了边界条件。

按日期查询预约：

```powershell
curl.exe -i "http://127.0.0.1:5055/bookings?date=2026-06-10"
```

期望看到：

```text
HTTP/1.1 200 OK
```

响应体中应包含 active 预约，并按开始时间排序。

取消第一个预约：

```powershell
curl.exe -i -X DELETE http://127.0.0.1:5055/bookings/1
```

期望看到：

```text
HTTP/1.1 204 NO CONTENT
```

再次查询：

```powershell
curl.exe -i "http://127.0.0.1:5055/bookings?date=2026-06-10"
```

怎么解释：

被取消的预约不应再出现在 active 列表中。取消后同一时间段可以重新预约，这是隐藏 oracle 也会覆盖的业务行为。

结束 API 演示：

回到运行 Flask 的第一个 PowerShell 窗口，按 `Ctrl+C` 停止服务，然后执行：

```powershell
Pop-Location
```

这一整段的答辩意义：

> 我们不是只展示 benchmark 分数，而是从 benchmark 生成目录中启动了 Agent 写出的软件，并用真实 HTTP 请求体验了健康检查、会议室创建、预约创建、冲突检测、边界条件和取消预约。这说明 CodeAgent 的输出产物是可运行、可验证、可解释的软件项目。

## 4. 半交互式使用案例：wizard 创建待办事项 CLI 软件

这是第二条主线。它展示用户不写 YAML 时，如何通过半交互向导创建任务，并继续用生成的配置驱动真实 Agent 运行。

这个案例使用 `01_todo_manager` 的公开需求作为输入。它和 benchmark 仍然不是同一次运行：这里的目的不是隐藏 oracle 评分，而是展示普通用户如何通过 wizard 把一个需求文档变成一个可运行的 CLI 软件。

### 4.1 介绍半交互案例的任务

查看需求：

```powershell
Get-Content -LiteralPath benchmark\selfbuilt\cases\01_todo_manager\input\requirements.md -Encoding UTF8
```

你需要向观众解释：

这个任务要求生成一个命令行待办事项管理工具，入口是：

```text
python -m todo_manager --file tasks.json <command> [options]
```

它需要支持：

- `add` 添加任务。
- `list` 查看任务。
- `done` 标记完成。
- `delete` 删除任务。
- 使用 JSON 文件持久化。
- 对空标题、错误日期、非法任务 ID、损坏 JSON 等异常输入返回错误。

这个案例适合半交互演示，因为观众能很快理解“待办事项工具”是什么，也能在终端中直接体验生成的 CLI。

### 4.2 准备一个干净的半交互演示目录

操作命令：

```powershell
$todoDemo = "codeagent_runs\interactive_demo\todo_manager"
Remove-Item -LiteralPath $todoDemo -Recurse -Force -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Path "$todoDemo\workspace" -Force | Out-Null
Copy-Item -LiteralPath benchmark\selfbuilt\cases\01_todo_manager\input\requirements.md -Destination "$todoDemo\requirements.md"
```

这一步在做什么：

创建一个独立演示目录，不直接修改 benchmark 原始 case。`workspace` 初始为空，`requirements.md` 是用户提供给 Agent 的需求材料。

期望看到什么：

这组命令通常没有输出。可以用下面命令确认：

```powershell
Get-ChildItem -LiteralPath $todoDemo -Recurse
```

怎么解释：

半交互案例模拟普通用户自己的项目目录：一个空 workspace 加一份需求文档。这样不会污染 benchmark 原始数据，也便于反复演示。

### 4.3 启动 wizard

操作命令：

```powershell
python -m codeagent wizard
```

按下面方式回答提示：

```text
Stages (comma-separated, contiguous) [implement,test,debug,repair]: implement,test,debug,repair
Project path [.]: codeagent_runs\interactive_demo\todo_manager\workspace
Input material path (blank to skip): codeagent_runs\interactive_demo\todo_manager\requirements.md
Output directory [codeagent_runs]: codeagent_runs\interactive_demo\todo_manager\runs
Test command [pytest -q]: python -m pytest -q
Initialize run with this task configuration? [Y/n]: y
```

这一步在展示什么：

wizard 把用户输入转成规范化 `TaskConfig`。它会校验路径、解析阶段列表、记录输入材料、输出目录和测试命令，然后创建一个 run directory。

期望看到什么：

终端会打印任务摘要：

```text
Task Summary
============
Stages: implementation, testing, debugging, repair
Project: D:\Projects\CodeAgent\codeagent_runs\interactive_demo\todo_manager\workspace
Output directory: D:\Projects\CodeAgent\codeagent_runs\interactive_demo\todo_manager\runs
Test command: python -m pytest -q
Input materials:
- requirements: D:\Projects\CodeAgent\codeagent_runs\interactive_demo\todo_manager\requirements.md
```

确认后会看到：

```text
Run initialized: <run_id>
Run directory: <wizard_run_dir>
```

怎么解释：

这里的 wizard 不是为了替代 Agent 执行，而是为了让用户不用手写 YAML。它把半交互输入变成可复现的 `task_config.yaml`、`metadata.json`、`checkpoints.sqlite` 和初始化报告。

### 4.4 查看 wizard 生成的配置

操作命令：

```powershell
$wizardRun = Get-ChildItem -LiteralPath "$todoDemo\runs" -Directory |
  Sort-Object LastWriteTime -Descending |
  Select-Object -First 1
Get-Content -LiteralPath (Join-Path $wizardRun.FullName "task_config.yaml") -Encoding UTF8
```

这一步在展示什么：

展示半交互输入已经固化成配置文件。重点看：

- `stages` 是否为 `implementation, testing, debugging, repair`。
- `project_path` 是否指向干净 workspace。
- `input_materials` 是否包含 requirements。
- `test_command` 是否为 `python -m pytest -q`。
- `mode` 是否为 `wizard`。

怎么解释：

这份 `task_config.yaml` 就是后续运行的唯一输入。它让半交互操作也可以被复现、审计和归档。

### 4.5 用 wizard 生成的配置运行 Agent

操作命令：

```powershell
$todoConfig = Join-Path $wizardRun.FullName "task_config.yaml"
python -m codeagent run --config $todoConfig
```

这一步在做什么：

使用 wizard 生成的配置启动真实 Agent。此时会调用 OpenRouter LLM，让 Agent 根据待办事项需求在空 `workspace` 中生成 CLI 项目。

终端上期望看到什么：

```text
[route] entry -> implementation
[stage] implementation completed
[stage] testing completed
[final] succeeded
Run directory: D:/Projects/CodeAgent/codeagent_runs/interactive_demo/todo_manager/runs/<agent_run_id>
Final status: succeeded
```

怎么解释：

- wizard 负责把用户意图变成配置。
- `run --config` 负责执行 LangGraph 工作流。
- implementation 阶段会生成代码 patch。
- testing 阶段会运行配置中的测试命令。
- 如果测试失败，图会按状态进入 debugging/repair。

### 4.6 查看半交互 Agent run 的产物

操作命令：

```powershell
$todoAgentRun = Get-ChildItem -LiteralPath "$todoDemo\runs" -Directory |
  Sort-Object LastWriteTime -Descending |
  Select-Object -First 1
Get-Content -LiteralPath (Join-Path $todoAgentRun.FullName "final_report.md") -Encoding UTF8
Get-ChildItem -LiteralPath "$todoDemo\workspace" -Recurse -File |
  Where-Object { $_.FullName -notmatch "__pycache__" } |
  Select-Object FullName
```

这一步在展示什么：

先看 Agent 的审计报告，再看生成的软件文件。待办事项 CLI 一般会生成类似：

```text
workspace\todo_manager\__init__.py
workspace\todo_manager\__main__.py
workspace\todo_manager\...
```

怎么解释：

这证明半交互输入最后落到了真实软件产物上，而不是停留在“创建了一个配置文件”。

### 4.8 解释半交互案例和 benchmark 案例的区别

答辩时可以这样说：

| 对比项 | 非交互式 benchmark | 半交互式 wizard |
|---|---|---|
| 目标 | 评测 Agent 生成软件的能力 | 展示普通用户如何创建任务 |
| 输入方式 | benchmark YAML 批量定义 case | 终端逐项输入任务信息 |
| 输出 | benchmark 聚合报告、case 副本、oracle 日志 | wizard run、task_config、Agent run、生成软件 |
| 是否隐藏评测 | 是，使用 `oracle_tests` | 否，主要展示用户体验 |
| 是否修改原始 benchmark | 否，runner 复制到干净目录 | 否，演示目录在 `codeagent_runs` 下 |

这张表的意义：

它帮助观众理解两个案例不是重复展示。第一个案例证明“能力和分数”，第二个案例证明“用户如何使用产品”。

## 5. 演示时如何解释运行产物

无论哪个案例，CodeAgent run directory 中都可以重点解释这些文件：

| 文件 | 含义 | 演示时怎么说 |
|---|---|---|
| `metadata.json` | 本次运行元数据 | 记录 run_id、模型、阶段、项目路径、checkpoint 配置 |
| `task_config.yaml` | 规范化任务配置 | 证明运行可复现 |
| `transcript.jsonl` | 工具和阶段事件记录 | 说明 Agent 做过什么 |
| `decision_trace.jsonl` | 审批和自动决策记录 | 说明 patch 和命令执行不是无痕发生 |
| `checkpoints.sqlite` | LangGraph checkpoint | 支撑 resume 和中断恢复 |
| `implementation/implementation.patch.diff` | LLM 生成并被系统应用的 patch | 证明 patch-first 代码写入 |
| `implementation/implementation_report.md` | 实现阶段说明 | 解释 Agent 为什么这么改 |
| `testing/test_report.md` | 测试阶段报告 | 说明测试命令和解析结果 |
| `final_report.md` | 最终汇总 | 给答辩老师快速看结论 |

讲解原则：

- 先讲“这个文件回答什么问题”，再打开文件。
- 不要只说“生成了很多文件”，要把文件和审计问题对应起来。
- benchmark 的隐藏 oracle 只讲结果和日志目录，不打开隐藏测试源码。

## 7. 常见问题和现场解释

### 7.1 为什么非交互案例要用自建 benchmark？

因为它最接近课程项目目标：Agent 从需求出发生成完整软件，再由隐藏测试评测。普通示例只能说明 CLI 能跑，自建 benchmark 能说明 Agent 在真实软件工程任务中有效。

### 7.2 为什么 benchmark 里还要打开生成的软件手动体验？

benchmark 分数证明“符合评测标准”，手动体验证明“人能理解并使用这个软件”。两者结合，比只看分数或只看界面都更有说服力。

### 7.3 `oracle_success=True` 和 `final_status=succeeded` 有什么区别？

`final_status=succeeded` 是 Agent 工作流自己的结束状态。`oracle_success=True` 是 benchmark evaluator 对隐藏验收测试的结果。答辩时应强调最终质量以 oracle 评测为准。

### 7.4 `source_unchanged=True` 说明什么？

说明原始 benchmark case 在运行前后哈希一致。Agent 写代码发生在复制出来的 `case_workspaces` 中，所以同一个 benchmark 可以反复运行。

### 7.5 为什么半交互 wizard 后还要运行 `run --config`？

当前 wizard 的职责是引导用户创建并保存规范化任务配置，不直接执行完整 Agent。这样设计的好处是：用户可以先检查配置，再决定何时执行；执行阶段仍走统一的 `run --config` 工作流。

### 7.6 如果 Flask 端口被占用怎么办？

把端口换成另一个值，例如：

```powershell
python -m flask --app "meeting_room_booking:create_app" run --host 127.0.0.1 --port 5056
```

后续 `curl.exe` 里的端口也改成 `5056`。

### 7.7 如果生成的 todo CLI 包名不是预期怎么办？

优先查看半交互 run 的 `implementation\changed_files.json` 和 workspace 文件列表，确认 Agent 实际生成了什么。正式展示前建议先跑通一次半交互案例，使用通过验证的 run 作为课堂演示材料。

## 8. 结尾总结词

可以用下面这段话收尾：

> 本次展示只用了两个案例。第一个是非交互式自建 benchmark，证明 CodeAgent 能在真实 LLM 调用下从空目录生成多个软件项目，并通过隐藏 oracle；其中会议室预约 API 还能被我们现场启动和调用。第二个是半交互 wizard，证明普通用户可以通过终端向导创建任务，再用生成配置驱动 Agent 生成可运行的 CLI 软件。结合运行产物、patch、日志、decision trace、checkpoint 和 benchmark 报告，可以看到 CodeAgent 不只是生成代码，而是在按软件工程流程生成、验证、记录和评测软件。
