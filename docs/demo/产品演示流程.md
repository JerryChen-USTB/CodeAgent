# CodeAgent 产品演示流程

本文档面向课程展示和答辩，目标是在有限时间内清晰展示 CodeAgent 的定位、运行方式、关键工程能力和 benchmark 结果。演示建议分为“环境检查、非交互运行、半交互运行、产物讲解、benchmark 结果讲解、答辩问答”六个部分。

## 1. 演示目标

演示结束后，听众应能看到：

- CodeAgent 是一个本地 CLI 软件工程智能体，可以围绕 `implement -> test -> debug -> repair` 执行软件工程任务。
- 系统通过 LangGraph 编排阶段工作流，通过 LangChain/OpenRouter 调用真实 LLM。
- 所有副作用都有 patch-first、HITL 或 benchmark auto-approval 记录，运行过程可审计、可复现。
- 每次运行都会生成结构化产物，包括 `metadata.json`、`task_config.yaml`、`transcript.jsonl`、`decision_trace.jsonl`、`artifacts_index.json`、`checkpoints.sqlite`、阶段报告和 `final_report.md`。
- benchmark 在干净复制的 case workspace 中运行，原始 case 不被破坏，可以重复利用。

## 2. 演示前准备

### 2.1 安装依赖

在项目根目录执行：

```powershell
python -m pip install -e .
```

期望效果：

- 命令正常结束。
- `codeagent` 命令可用。

### 2.2 检查 CLI 入口

```powershell
python -m codeagent --help
codeagent --help
```

期望效果：

- 终端展示 CodeAgent 根命令帮助。
- 可以看到 `wizard`、`run`、`implement`、`test`、`debug`、`repair`、`benchmark`、`resume` 子命令。

### 2.3 检查 OpenRouter 环境变量

```powershell
python -c "import os; print('OPENROUTER_API_KEY configured:', bool(os.environ.get('OPENROUTER_API_KEY')))"
```

期望效果：

- 输出 `OPENROUTER_API_KEY configured: True`。
- 不要在终端、PPT 或文档中展示密钥内容。

如果当前终端没有读取到用户级环境变量，可以重新打开 PowerShell 或在当前进程临时设置：

```powershell
$env:OPENROUTER_API_KEY = "请填入你的 OpenRouter API Key"
```

## 3. 推荐展示流程总览

建议 15 至 25 分钟演示顺序：

| 阶段 | 时间 | 操作 | 展示重点 |
|---|---:|---|---|
| 环境检查 | 2 分钟 | `--help`、环境变量检查 | CLI 产品入口和真实 LLM 准备 |
| 非交互示例运行 | 3 分钟 | `run --config examples/task.yaml` | 路由、阶段执行、运行产物 |
| 半交互 wizard | 3 分钟 | `codeagent wizard` | 用户确认、配置生成、HITL 思路 |
| 产物讲解 | 4 分钟 | 打开 `final_report.md`、`artifacts_index.json`、`decision_trace.jsonl` | 可审计与可复现 |
| benchmark 讲解 | 5 分钟 | 展示已生成或现场运行 benchmark | 干净 workspace、成功率、隐藏 oracle 隔离 |
| 答辩问答 | 5 分钟 | 结合实现报告回答 | LangGraph/LangChain/patch-first/checkpoint |

## 4. 非交互方式运行

非交互运行适合课堂现场快速展示，因为命令固定、输出稳定、不会要求人工输入。

### 4.1 运行示例任务

```powershell
python -m codeagent run --config examples\task.yaml
```

期望看到的终端效果：

- 出现类似 `[stage] route_entry completed` 的阶段事件。
- 出现类似 `[route] entry -> debugging: start selected stage debug` 的路由信息。
- 运行结束时显示：

```text
[final] succeeded
Run directory: D:/Projects/CodeAgent/codeagent_runs/examples/<run_id>
Final status: succeeded
```

说明：

- `examples/task.yaml` 是一个 debug-only 示例，使用公开 failure log，不需要修改业务代码。
- 该示例适合演示运行目录、报告生成、阶段结果，而不是演示真实 LLM 修复能力。

### 4.2 查看运行产物

将上一步输出中的 `Run directory` 复制出来，执行：

```powershell
Get-ChildItem -LiteralPath "<Run directory>"
```

期望看到的文件和目录：

```text
metadata.json
task_config.yaml
transcript.jsonl
decision_trace.jsonl
artifacts_index.json
checkpoints.sqlite
final_report.md
debugging/
implementation/
testing/
repair/
benchmark/
```

### 4.3 打开最终报告

```powershell
Get-Content -LiteralPath "<Run directory>\final_report.md" -Encoding UTF8
```

期望效果：

- 报告展示最终状态、阶段摘要和下一步建议。
- 报告内容来自阶段结果和 artifact index，不依赖 LLM 临场编造。

### 4.4 展示结构化审计文件

```powershell
Get-Content -LiteralPath "<Run directory>\artifacts_index.json" -Encoding UTF8
Get-Content -LiteralPath "<Run directory>\transcript.jsonl" -Encoding UTF8
Get-Content -LiteralPath "<Run directory>\decision_trace.jsonl" -Encoding UTF8
```

期望效果：

- `artifacts_index.json` 能看到本次运行登记过的报告、日志、配置和阶段产物。
- `transcript.jsonl` 能看到阶段事件。
- `decision_trace.jsonl` 在普通示例中可能为空；在包含审批或 benchmark auto-approval 的运行中会记录决策。

## 5. 半交互方式运行

半交互方式适合展示用户如何参与任务配置和审批流程。课堂演示建议使用 wizard 展示配置确认，再结合 benchmark 或阶段运行的 `decision_trace.jsonl` 解释 HITL 与 auto-approval。

### 5.1 启动 wizard

```powershell
python -m codeagent wizard
```

按提示输入：

```text
Stages (comma-separated, contiguous): debug
Project path: examples\debug_project
Input material path (blank to skip): examples\debug_project\failing.log
Output directory: codeagent_runs\demo_wizard
Test command: pytest -q
Initialize run with this task configuration? Yes
```

期望效果：

- 终端先展示 `Task Summary`。
- 用户确认后，系统创建一个新的 run directory。
- 终端显示：

```text
Run initialized: <run_id>
Run directory: <path>
```

说明：

- 当前 wizard 的职责是引导用户生成并确认任务配置，然后初始化可审计运行目录。
- 如果在确认问题处选择 No，系统会写入取消报告，体现半交互流程中的取消路径。

### 5.2 查看 wizard 初始化产物

```powershell
Get-ChildItem -LiteralPath "codeagent_runs\demo_wizard"
```

期望效果：

- 能看到由 wizard 创建的 run 子目录。
- 子目录中包含 `metadata.json`、`task_config.yaml`、`artifacts_index.json`、`checkpoints.sqlite` 等基础产物。

### 5.3 展示 resume/inspect 能力

选取一个已有 run id：

```powershell
python -m codeagent resume --run-id <run_id>
```

期望效果：

- 如果运行已经完成，终端展示可读摘要和 final report 摘要。
- 如果运行存在 pending interrupt，终端展示 pending interrupt 信息，用户可以用 `--decision-json` 继续。

示例决策格式：

```powershell
python -m codeagent resume --run-id <run_id> --decision-json '{"decision":"approve","interrupt_id":"testing_command"}'
```

说明：

- 真实 pending interrupt 取决于当次任务是否在 HITL 节点暂停。
- benchmark 模式不会停下来等待人工输入，但会把 auto-approval 写入 `decision_trace.jsonl`，用于答辩时解释“自动化评测”和“可审计审批”如何兼容。

## 8. 常见答辩问题提示

### 为什么选择 CLI 而不是 IDE 插件？

本轮实现以 SRS 和设计文档确定的 CLI 范围为准。CLI 更适合课程演示、自动化测试、benchmark 复现和运行产物审计。IDE、LSP、Web 前端保留为后续扩展方向。

### 如何保证 LLM 不直接乱改代码？

系统采用 patch-first。LLM 只能生成计划和 unified diff；diff 会经过路径、敏感文件、隐藏 benchmark 路径和风险规则检查，然后由 PatchService 应用。普通模式下副作用需要 HITL 审批，benchmark 模式下自动审批也会写入 decision trace。

### 如何保证 benchmark case 可重复利用？

BenchmarkRunner 会把原始 case 复制到每次 benchmark 的独立 run workspace。智能体只看到配置允许的 visible paths，只能修改复制后的 workspace。runner 会记录 source snapshot 并在报告中给出 `source_unchanged=True`。

### 如何处理真实 LLM 波动？

系统使用结构化输出 schema、有限重试、明确 prompt 约束、错误报告和回归 benchmark 降低波动风险。真实 LLM 仍然可能受模型版本、上下文和响应格式影响，因此报告中保留失败原因、日志和 artifact 路径。

### checkpoint/resume 展示什么价值？

每个 run 使用 `run_id` 作为 LangGraph `thread_id`，并写入 `checkpoints.sqlite`。当流程在审批点暂停或异常中断时，可以通过 `resume` 查看状态或继续提交决策；即使 checkpoint 不可恢复，也能从 artifact index 和 final report 做只读检查。

## 9. 演示注意事项

- 现场不要展示 OpenRouter API Key 的值。
- 现场运行完整 benchmark 前，确认网络和 OpenRouter 余额。
- benchmark 输出目录较多，展示时优先打开 `benchmark_report.md` 和单个 case 的 `final_report.md`。
- BugsInPy blocker 是环境限制，不是静默失败；答辩时应主动说明。
- `codeagent_runs/` 和 benchmark 运行产物已被忽略，不需要提交到 Git。
- 如果现场时间紧，优先跑 `examples/task.yaml`，然后展示已完成的真实 benchmark 报告。
