# 1. 引言

## 1.1 编写目的

本文档用于描述“基于大语言模型的软件工程智能体”项目的需求规格，明确系统应当实现的功能范围、用户角色、输入输出形式、业务流程、数据需求、外部接口、非功能需求和验收标准。

需求规格说明书的核心作用是说明软件系统“要做什么、给谁用、做到什么程度、怎么验收”，而不是详细描述代码实现方案；本文档将遵循该原则，重点描述系统需求，并为后续系统设计、开发、测试和课程验收提供依据。

本文档面向以下对象：

| 对象            | 用途                                 |
| --------------- | ------------------------------------ |
| 项目组成员      | 明确开发范围、功能边界、分工依据     |
| 系统设计人员    | 根据需求设计架构、模块和数据流       |
| 开发人员        | 根据功能需求实现 CLI 智能体系统      |
| 测试人员        | 根据验收标准设计测试用例和 benchmark |
| 课程教师 / 助教 | 检查项目是否满足课程设计要求         |

## 1.2 项目背景

本项目来源于软件工程课程设计选题“基于大语言模型的软件工程智能体”。课程要求学生设计并实现一个面向软件项目开发的智能体系统，使其能够在一个或多个连续开发阶段中辅助或自动完成典型软件工程任务，并掌握任务分解、上下文管理、工具调用等智能体关键技术。

本项目选择覆盖软件工程中的四个连续阶段：

```text
实现 → 测试 → 调试 → 修复
```

课程题目中给出的最小组合包括“实现 + 测试”和“调试 + 程序修复”：前者要求根据需求、PRD 或设计模型生成可运行程序代码和单元测试，并执行测试、汇总结果；后者要求给定错误程序和触发错误的测试用例，自动定位错误位置、解释错误原因并生成修复后的正确代码。

因此，本项目不是一个普通代码生成器，而是一个面向 CLI 的软件工程智能体，能够围绕项目仓库执行以下闭环：

```text
读取需求 / 设计材料
→ 规划实现方案
→ 生成或修改代码
→ 制定测试方案
→ 人工审核测试方案
→ 生成并执行测试
→ 分析失败日志
→ 定位错误原因
→ 生成修复补丁
→ 再次运行测试验证
→ 输出全过程报告
```

# 2. 总体描述

## 2.1 产品定位

本系统是一个基于大语言模型的软件工程智能体原型，面向软件开发任务，提供 CLI 形式的智能辅助能力。

系统能够根据用户提供的需求文档、PRD、用户故事、API 规格、设计模型、项目骨架、技术约束和验收条件等输入材料，完成以下工作：

```text
1. 根据输入材料生成或修改代码；
2. 根据需求和代码生成测试方案与测试用例；
3. 执行测试并汇总测试结果；
4. 根据失败测试和错误日志定位问题；
5. 生成修复补丁并再次验证；
6. 输出完整的过程日志、测试报告和修复报告。
```

系统的目标不是完全替代开发者，而是在开发者监督下完成工程任务。系统应当通过半交互式 CLI 提示用户选择阶段、选择输入材料、确认测试方案、批准代码修改和测试执行，使用户能够掌握 Agent 当前正在做什么。

------

## 2.2 技术定位

本项目计划采用：

```text
LangGraph + LangChain + Python CLI
```

其中：

| 技术               | 在本项目中的定位                                             |
| ------------------ | ------------------------------------------------------------ |
| LangGraph          | 负责实现阶段化工作流、状态流转、Checkpoint、人机交互中断、恢复执行、流式进度输出 |
| LangChain          | 负责大模型接口、消息抽象、工具调用、Agent 基础能力、模型供应商适配 |
| Python CLI         | 负责用户交互、文件路径输入、菜单选择、进度展示、结果输出     |
| 本地文件系统       | 负责读取输入材料、扫描项目、写入代码、测试、报告和日志       |
| Shell / Subprocess | 负责执行构建命令、测试命令和必要的项目命令                   |

LangGraph 官方文档将其描述为用于构建、管理和部署长时间运行、有状态 Agent 的低层编排框架，重点能力包括 durable execution、streaming、human-in-the-loop 和 persistence。([LangChain Docs](https://docs.langchain.com/oss/python/langgraph/overview)) LangChain 官方文档则说明其提供预构建 Agent 架构、模型和工具集成，并标准化不同模型供应商的交互接口；LangChain 的 Agent 也构建在 LangGraph 之上，以利用 durable execution、human-in-the-loop 和 persistence 等能力。([LangChain Docs](https://docs.langchain.com/oss/python/langchain/overview))

# 3. 阶段输入输出规格

## 3.1 四阶段总览

| 阶段 | 阶段目标                                   | 输入                                                         | 输出                                       |
| ---- | ------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------ |
| 实现 | 根据需求或设计材料生成 / 修改代码          | 需求文档、PRD、用户故事、API 规格、设计模型、项目骨架、技术约束、验收条件 | 代码文件、补丁、实现报告、构建日志         |
| 测试 | 根据需求和代码生成测试方案、测试用例并执行 | 项目代码、需求材料、测试框架、测试命令、验收条件             | 测试方案、测试文件、测试报告、执行日志     |
| 调试 | 根据失败测试和日志定位问题                 | buggy 项目、失败测试、测试命令、错误日志、预期行为           | 错误复现报告、失败摘要、错误定位、根因分析 |

> 在连续阶段中，前一阶段的输出应当能够作为后一阶段的输入

# 4. CLI 交互需求

## 4.1 CLI 运行模式

系统应支持三种 CLI 运行模式：

| 模式             | 说明                                 | 示例                                                     |
| ---------------- | ------------------------------------ | -------------------------------------------------------- |
| 半交互式向导模式 | 用户通过选择题和路径输入逐步配置任务 | `codeagent wizard`                                       |
| 非交互式命令模式 | 用户通过命令参数一次性指定任务       | `codeagent run --stages implement,test --project ./repo` |
| 配置文件模式     | 用户通过 YAML / JSON 配置任务        | `codeagent run --config task.yaml`                       |

------

## 4.2 半交互式向导流程

系统启动后应按照以下步骤与用户交互：

```text
1. 显示欢迎信息和当前工作目录；
2. 询问用户选择执行模式；
3. 询问用户选择阶段；
4. 若选择多个阶段，校验阶段是否连续；
5. 按阶段列出所需输入材料；
6. 对每类材料提示必选 / 可选 / 多选规则；
7. 用户输入文件路径，回车新增一项；
8. 用户输入空行或选择“完成”结束当前材料输入；
9. 系统校验路径存在性、格式和必选项；
10. 系统展示任务摘要；
11. 用户确认后开始执行；
12. 执行过程中持续展示 Agent 当前状态；
13. 遇到需要人工监督的节点时暂停并等待用户决策；
14. 执行完成后展示输出目录和结果摘要。
```

------

## 4.3 阶段选择规则

| 选择                      | 是否允许 | 说明                                   |
| ------------------------- | -------- | -------------------------------------- |
| 只选择实现                | 允许     | 生成或修改代码，不自动测试             |
| 只选择测试                | 允许     | 对已有项目生成 / 执行测试              |
| 只选择调试                | 允许     | 分析失败日志和错误原因                 |
| 只选择修复                | 允许     | 根据已有调试信息或失败测试修复         |
| 实现 + 测试               | 允许     | 最小完整功能闭环                       |
| 测试 + 调试               | 允许     | 测试失败后进入调试                     |
| 调试 + 修复               | 允许     | 最小修复闭环                           |
| 实现 + 测试 + 调试        | 允许     | 若测试失败则调试                       |
| 测试 + 调试 + 修复        | 允许     | 常见已有代码修复流程                   |
| 实现 + 测试 + 调试 + 修复 | 允许     | 完整流水线                             |
| 实现 + 修复               | 不允许   | 阶段不连续                             |
| 测试 + 修复但不调试       | 【待定】 | 可允许直接修复，但建议默认要求调试阶段 |
| 调试 + 实现               | 不允许   | 顺序错误                               |

LangGraph 的 interrupt 机制支持在图执行过程中暂停、保存状态并等待外部输入后恢复，适合实现测试方案审核、补丁审批、命令执行确认等人机协作节点。([LangChain Docs](https://docs.langchain.com/oss/python/langgraph/interrupts)) LangChain 的 Human-in-the-loop middleware 支持在模型提出写文件、执行 SQL 等需要审查的工具调用时暂停，并由人工选择 approve、edit、reject 或 respond。([LangChain Docs](https://docs.langchain.com/oss/python/langchain/human-in-the-loop))

# 9. 典型用例

## 9.2 UC-01：半交互式完整流水线

| 项目     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 参与者   | 开发者                                                       |
| 前置条件 | 用户已进入项目目录；系统已配置模型 API；项目路径有效         |
| 基本流程 | 用户运行 `codeagent wizard` → 选择“实现+测试+调试+修复” → 选择输入材料 → 输入需求文档、项目骨架、测试命令 → 系统展示任务摘要 → 用户确认 → 系统生成实现计划 → 生成 / 修改代码 → 生成测试方案 → 用户审核批准 → 系统生成测试并执行 → 若测试失败，进入调试 → 输出根因分析 → 生成修复补丁 → 用户批准 → 应用补丁 → 重新运行测试 → 输出最终报告 |
| 异常流程 | 输入材料缺失；模型调用失败；用户拒绝测试方案；测试命令无法执行；补丁被用户拒绝 |
| 后置条件 | 输出目录包含实现报告、测试报告、调试报告、修复报告、patch、transcript 和 final_report |
| 验收标准 | 在至少一个示例项目中完整运行，并能展示每阶段产物             |

## 9.3 UC-02：根据需求实现功能

| 项目     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 参与者   | 开发者                                                       |
| 前置条件 | 用户提供需求文档和项目骨架                                   |
| 基本流程 | 用户选择实现阶段 → 输入需求文档和项目目录 → 系统分析项目结构 → 生成实现计划 → 用户确认 → 系统生成或修改代码 → 输出补丁和实现报告 |
| 异常流程 | 需求不清晰；项目目录不可读；用户拒绝修改                     |
| 后置条件 | 项目代码被更新或生成 patch                                   |
| 验收标准 | 代码语法正确，报告说明实现内容                               |

## 9.4 UC-03：生成并审核测试方案

| 项目     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 参与者   | 测试人员                                                     |
| 前置条件 | 用户提供项目代码、需求材料或实现报告                         |
| 基本流程 | 用户选择测试阶段 → 系统分析需求和代码 → 生成测试方案 → 系统暂停并展示测试方案 → 用户批准 / 修改 / 拒绝 → 批准后系统生成测试文件 → 用户批准测试命令 → 系统执行测试 → 输出测试报告 |
| 异常流程 | 用户拒绝方案；测试框架无法识别；测试命令失败                 |
| 后置条件 | 输出测试文件、测试日志、测试报告                             |
| 验收标准 | 测试方案经过人工审核，测试命令结果被保存                     |

## 9.5 UC-04：根据失败日志调试问题

| 项目     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 参与者   | 开发者                                                       |
| 前置条件 | 用户提供 buggy 项目、错误日志或测试命令                      |
| 基本流程 | 用户选择调试阶段 → 系统读取错误日志 → 尝试复现错误 → 搜索相关测试和源码 → 输出可疑位置排序 → 生成根因分析和修复建议 |
| 异常流程 | 错误无法复现；日志信息不足；相关源码不存在                   |
| 后置条件 | 输出调试报告、错误复现报告、fault_localization.json          |
| 验收标准 | 报告中包含失败测试、可疑文件、根因分析                       |

## 9.6 UC-05：修复 bug 并回归验证

| 项目     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 参与者   | 开发者                                                       |
| 前置条件 | 用户提供 buggy 项目、测试命令和调试报告                      |
| 基本流程 | 用户选择修复阶段 → 系统读取调试报告 → 生成修复计划 → 生成补丁 → 用户审核 diff → 用户批准 → 系统应用补丁 → 运行测试 → 若失败，在限制次数内再次修复 → 输出修复报告 |
| 异常流程 | 用户拒绝补丁；测试仍失败；补丁无法应用                       |
| 后置条件 | 生成修复补丁和验证日志                                       |
| 验收标准 | FAIL_TO_PASS 测试通过，回归测试尽量不失败；若未修复，报告说明原因 |

## 9.7 UC-06：批量运行 benchmark

| 项目     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 参与者   | 项目负责人                                                   |
| 前置条件 | 已准备至少 5 个 benchmark 案例                               |
| 基本流程 | 用户运行 `codeagent benchmark --config benchmark.yaml` → 系统依次运行案例 → 每个案例保存独立产物 → 系统统计成功率 → 输出 benchmark_summary |
| 异常流程 | 某案例配置错误；某案例运行超时；某案例测试命令失败           |
| 后置条件 | 输出 benchmark 报告                                          |
| 验收标准 | 报告包含至少 5 个案例的结果和总体成功率                      |

## 9.8 UC-07：从中断任务恢复

| 项目     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 参与者   | 开发者                                                       |
| 前置条件 | 系统启用 checkpoint；任务曾中断                              |
| 基本流程 | 用户运行 `codeagent resume --run-id <run_id>` → 系统读取 checkpoint → 展示上次中断位置 → 用户确认继续 → 系统从最近节点恢复 |
| 异常流程 | checkpoint 缺失；项目文件已变化；模型配置不可用              |
| 后置条件 | 任务继续运行或输出无法恢复原因                               |
| 验收标准 | 至少能恢复到可查看中断前状态；是否继续执行列为 P2            |
