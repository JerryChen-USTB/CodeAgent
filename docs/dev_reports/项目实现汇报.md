# CodeAgent 项目实现汇报

本文档面向开发者和课程答辩评审，汇报 CodeAgent 从需求、设计、计划到实现、测试和 benchmark 的完整完成情况。文档内容以 `docs/codex/plans.md`、当前代码实现、开发报告、README、benchmark 运行产物和测试结果为依据。

## 1. 项目完成情况概述

CodeAgent 已实现为一个本地 Python CLI 软件工程智能体，支持围绕 `implement -> test -> debug -> repair` 的连续工程工作流，也支持合法的单阶段或连续阶段子集。系统使用 LangGraph 管理主工作流、阶段子图、条件路由、interrupt 和 checkpoint/resume；使用 LangChain 的 OpenAI-compatible ChatOpenAI 客户端通过 OpenRouter 调用真实 LLM，当前默认模型为 `google/gemini-3.5-flash`。

项目已完成以下核心能力：

- CLI：`wizard`、`run`、`implement`、`test`、`debug`、`repair`、`benchmark`、`resume` 命令。
- 配置系统：YAML/JSON 任务配置、阶段连续性校验、路径校验、默认模型和权限配置。
- LangGraph 工作流：主图和 implementation/testing/debugging/repair 四个阶段子图。
- LangChain/LLM：OpenRouter 模型工厂、结构化输出重试、角色 prompt registry。
- patch-first：LLM 生成计划和 diff，PatchService 负责校验、风险检查和应用。
- HITL：审批请求、审批决策、普通模式人工审批、benchmark 模式可审计 auto-approval。
- checkpoint/resume：每个 run 写入 SQLite checkpoint，支持 inspect 和恢复 pending interrupt。
- 日志与报告：每个 run 生成 metadata、task config、transcript、decision trace、artifact index、stage report、final report。
- benchmark：公开 benchmark、自建 benchmark、case 隔离复制、隐藏 oracle 路径隔离、聚合报告。
- 安全：本地 secret 文件不纳入项目读取和提交，OpenRouter 密钥只从环境变量解析，报告和 metadata 只记录环境变量名。
- M28 收尾增强：Agent testing 阶段由 LLM 生成可见测试并执行，0 测试结果会失败；wizard 已改为中文表单并确认后直接运行；CLI 运行过程会流式打印阶段内 LLM、补丁、命令和测试结果状态。

## 3. 核心功能与模块实现方法

### 3.1 CLI 接入层

主要文件：

- `codeagent/cli/app.py`
- `codeagent/cli/wizard.py`
- `codeagent/cli/executor.py`
- `codeagent/cli/resume.py`
- `codeagent/cli/progress.py`
- `codeagent/cli/approval_console.py`

CLI 使用 Typer 实现。`app.py` 定义根命令和子命令；`wizard.py` 负责中文半交互表单、阶段选择、多选输入材料、任务摘要确认，并在确认后直接启动 Agent；`executor.py` 将 TaskConfig 转为 RunContext 和阶段 handler，再执行主工作流；`resume.py` 读取 run directory、checkpoint 和 artifact，支持查看已完成运行或恢复 pending interrupt；`progress.py` 将图事件格式化为中文用户可读输出。

CLI 支持两类运行方式：

- 非交互：`codeagent run --config examples/task.yaml` 或 stage subcommands。
- 半交互：`codeagent wizard` 收集和确认任务配置后直接运行 Agent，同时保存 `task_config.yaml` 以便审计和复现；Graph interrupt/resume 机制可在审批点暂停并恢复。

### 3.2 配置与运行初始化

主要文件：

- `codeagent/config/schema.py`
- `codeagent/config/loader.py`
- `codeagent/config/validators.py`
- `codeagent/config/defaults.py`
- `codeagent/runtime/run_context.py`

配置模型使用 Pydantic。`TaskConfig` 描述阶段、项目路径、输入材料、测试命令、可见路径、模型配置、权限和运行策略；`BenchmarkConfig` 和 `BenchmarkCaseConfig` 描述 benchmark 套件。阶段校验要求阶段子集必须合法并保持连续，例如 `test,debug,repair` 合法，跳过中间阶段的非连续组合会被拒绝。

`create_run_context` 为每次运行创建唯一 run directory，并写入：

- `metadata.json`
- `task_config.yaml`
- `transcript.jsonl`
- `decision_trace.jsonl`
- `artifacts_index.json`
- `checkpoints.sqlite`
- implementation/testing/debugging/repair/benchmark 子目录

Windows 长路径和文件锁问题通过 `codeagent/filesystem.py` 的 helper 与 SQLite 连接关闭回归测试加固。

### 3.3 项目上下文系统

主要文件：

- `codeagent/context/scanner.py`
- `codeagent/context/file_reader.py`
- `codeagent/context/code_search.py`
- `codeagent/context/sensitive_filter.py`
- `codeagent/context/path_utils.py`

上下文系统负责为 LLM 和阶段服务提供受控项目视图。Scanner 会识别 Python 源码、测试、配置和依赖文件，同时跳过 `.git`、虚拟环境、构建目录、运行产物和敏感路径。FileReader 支持受限读取和长内容截断；CodeSearch 使用文本搜索返回摘要；SensitiveFilter 对 secret、隐藏 benchmark 路径和越界路径做拦截。

在 benchmark 模式下，agent 只能看到 `agent_visible_paths` 中声明的内容；`oracle_tests`、`evaluation`、`expected_result.json` 等路径不进入 LLM 上下文。

### 3.4 Agent 与 Prompt 系统

主要文件：

- `codeagent/agents/prompts.py`
- `codeagent/agents/plan_generation.py`
- `codeagent/models/structured_outputs.py`

PromptRegistry 将不同角色的系统 prompt 和任务 prompt 集中维护，覆盖 Planner、Coder、Test Designer、Debugger、Repairer、Verifier 等角色。核心约束包括：

- patch-first：只能提出 unified diff，不能直接写文件。
- no-secret：不得读取、输出或推断本地 secret。
- hidden oracle isolation：不得引用 benchmark 隐藏路径。
- schema output：模型响应必须满足结构化 schema。
- audit summary：生成结果要能映射到报告和 artifact。

`PlanGenerationService` 使用结构化输出 schema 解析 LLM 响应，并对 malformed/partial response 进行有限重试或输出可操作错误。

## 4. LangGraph 工作流实现方式

### 4.1 主图

主要文件：

- `codeagent/workflow/main_graph.py`
- `codeagent/workflow/routing.py`
- `codeagent/workflow/state.py`
- `codeagent/workflow/factory.py`
- `codeagent/workflow/events.py`

主图使用 LangGraph `StateGraph`。状态由 `AgentState` 承载，包含 task config、run context、stage results、messages、pending interrupt、repair attempts 等 checkpoint-safe 字段。

主图职责：

1. 加载并记录任务配置。
2. 初始化 run context。
3. 扫描项目上下文。
4. 按 selected stages 路由到对应阶段。
5. 根据阶段结果决定继续、跳转 debug、进入 repair loop 或结束。
6. 写入 final report。

路由策略示例：

- implementation 成功且包含 testing 阶段时进入 testing。
- testing 失败且包含 debugging 阶段时进入 debugging。
- debugging 成功且包含 repair 阶段时进入 repair。
- repair 后重新运行测试，直到成功或达到 `max_repair_attempts`。

### 4.2 四个阶段子图

主要文件：

- `codeagent/workflow/subgraphs/implementation.py`
- `codeagent/workflow/subgraphs/testing.py`
- `codeagent/workflow/subgraphs/debugging.py`
- `codeagent/workflow/subgraphs/repair.py`

Implementation 子图：

- 读取需求和项目上下文。
- 调用 LLM 生成 implementation plan 和 patch。
- 校验 patch 路径、风险和敏感文件。
- 在审批后应用 patch。
- 执行轻量语法检查。
- 写入 implementation report 和 stage result。

Testing 子图：

- 调用 LLM 基于公开需求和可见实现生成 `TestingPlan`。
- 触发 test plan review interrupt。
- 生成测试 patch。
- 触发 patch approval interrupt。
- 应用测试 patch。
- 触发 command approval interrupt。
- 执行 Agent 自测命令并解析结果。
- 拒绝 0 tests、`py_compile`-only smoke check、`Ran 0 tests`、`NO TESTS RAN`、`collected 0 items` 等无效成功证据。

Debugging 子图：

- 收集测试失败日志或用户提供的 failure log。
- 可选执行复现命令。
- 基于日志和代码搜索生成疑点排序、根因和修复计划。
- 写入 debugging report 和 stage result。

Repair 子图：

- 基于 debugging 输出和项目上下文生成 repair plan。
- 生成 repair patch。
- 运行风险检查和审批。
- 应用 patch 后执行回归测试。
- 成功则结束，失败则按路由进入下一轮 debug/repair 或达到上限后失败。

### 4.3 interrupt 与 resume

阶段子图中通过 LangGraph `interrupt` 暂停审批点。pending interrupt 被写入 checkpoint，CLI 可用 `resume --run-id` 查看。恢复时，用户通过 `--decision-json` 提交 decision，系统再从 checkpoint 状态继续运行。

`CheckpointManager` 使用 SQLite 保存 checkpoint 和 pending interrupt。为避免 Windows 文件锁，项目后期将 SQLite 连接初始化和状态检查切换为 `contextlib.closing`，并补充了文件可删除的回归测试。

## 5. LangChain 工具调用实现方式

### 5.1 模型工厂

主要文件：

- `codeagent/models/factory.py`
- `codeagent/models/secrets.py`
- `codeagent/config/defaults.py`

`ModelClientFactory` 使用 `langchain_openai.ChatOpenAI` 创建 OpenRouter 兼容客户端：

- `base_url=https://openrouter.ai/api/v1`
- 默认 model：`google/gemini-3.5-flash`
- 默认 api key env：`OPENROUTER_API_KEY`
- 低 temperature、超时和 bounded retries
- 默认 `max_tokens=16384`，避免 OpenRouter 对过大的默认输出窗口预占预算；任务配置可覆盖。
- 模型错误进入报告前会脱敏 OpenRouter key 管理链接、用户标识和 key/token/password 类字段。

SecretResolver 只从进程环境变量或 Windows 用户级环境变量解析密钥，不读取本地密钥文件。序列化和报告只记录 env var 名称，不记录密钥值。

### 5.2 工具注册与权限

主要文件：

- `codeagent/tools/registry.py`
- `codeagent/tools/permissions.py`
- `codeagent/tools/hitl.py`

ToolRegistry 将工具按阶段和副作用属性注册。典型工具包括：

- readonly：scan、read、search、parse test output。
- side-effect：apply patch、run shell、write report、record artifact。
- denied：访问 secret、越界路径、隐藏 benchmark 评测路径等。

ToolPermissionPolicy 将工具调用分为 allow、ask、deny。普通模式下 side-effect 工具需要审批；benchmark 模式下使用明确的 auto-approval，并写入 decision trace。

### 5.3 Shell 和测试工具

主要文件：

- `codeagent/tools/shell_tools.py`
- `codeagent/tools/pytest_tools.py`
- `codeagent/adapters/pytest_adapter.py`
- `codeagent/adapters/unittest_adapter.py`
- `codeagent/adapters/test_result.py`

ShellRunner 执行经过批准的命令，记录：

- command
- cwd
- timeout
- exit code
- duration
- stdout/stderr
- 日志文件路径

命令策略默认允许安全的 pytest、unittest、py_compile 等测试相关命令，拒绝明显危险或越界命令。测试解析器优先解析 pytest 格式，并为 unittest 和未知输出提供 fallback。

## 6. CLI、HITL、patch-first、checkpoint/resume、日志与报告

### 6.1 CLI

CLI 是本项目的主要产品界面。`README.md` 中记录了常用命令：

```powershell
python -m codeagent run --config examples/task.yaml
python -m codeagent implement --project ./repo --requirements requirements.md
python -m codeagent test --project ./repo --test-cmd "pytest -q"
python -m codeagent debug --project ./repo --test-cmd "pytest -q"
python -m codeagent repair --project ./repo --test-cmd "pytest -q"
python -m codeagent benchmark --config benchmark/benchmark.yaml
python -m codeagent benchmark --config benchmark/selfbuilt/selfbuilt_benchmark.yaml
python -m codeagent resume --run-id <run_id>
```

### 6.2 HITL

HITL 通过 `ApprovalRequest` 和 `ApprovalDecision` 表示。决策类型包括 approve、edit、reject、respond、cancel。审批点包括：

- implementation patch approval
- testing plan review
- testing patch approval
- testing command approval
- debugging reproduction command approval
- repair patch approval
- repair regression command approval

普通模式下系统可在这些节点暂停；benchmark 模式为了自动化评测不会等待人工输入，但会记录 auto-approval，避免副作用没有审计痕迹。

### 6.3 patch-first

主要文件：

- `codeagent/services/patch_service.py`
- `codeagent/tools/patch_tools.py`
- `codeagent/tools/risk_checker.py`

patch-first 的流程是：

1. LLM 生成结构化计划和 unified diff。
2. PatchService 解析 diff。
3. 校验路径必须在项目根或复制后的 benchmark workspace 内。
4. 拒绝敏感文件、隐藏 benchmark 路径和越界路径。
5. RiskChecker 标记删除测试、跳过测试、硬编码 expected result 等风险。
6. 审批通过后应用 patch。
7. 写入 patch artifact、changed files 和 stage report。

该设计避免 LLM 直接写入项目文件，也让每一次变更都可以追踪和复查。

### 6.4 checkpoint/resume

每个 run 目录都有 `checkpoints.sqlite`。`run_id` 也是 LangGraph `thread_id`。`resume` 支持：

- 查找 run directory。
- 读取 checkpoint pending interrupt。
- 展示 final report 摘要。
- 对 pending interrupt 提交 `--decision-json` 并继续。
- checkpoint 不可恢复时，从 `artifacts_index.json`、`stage_result.json`、`final_report.md` 做只读 fallback。

### 6.5 日志与报告

主要文件：

- `codeagent/reports/artifact_store.py`
- `codeagent/reports/decision_trace.py`
- `codeagent/reports/transcript.py`
- `codeagent/reports/writer.py`
- `codeagent/reports/schemas.py`

根级产物：

- `metadata.json`
- `task_config.yaml`
- `transcript.jsonl`
- `decision_trace.jsonl`
- `artifacts_index.json`
- `checkpoints.sqlite`
- `final_report.md`

阶段级产物：

- `stage_result.json`
- 阶段报告 Markdown
- LLM 计划或调试报告
- patch 文件
- changed files 记录
- shell stdout/stderr 日志
- 测试解析结果 JSON

最终报告只根据实际 stage results、artifact index 和 decision trace 生成，不让模型补写不存在的结果。

## 7. Benchmark 设计、测试方案与测试结果

### 7.1 Benchmark 设计

主要文件：

- `benchmark/benchmark.yaml`
- `benchmark/selfbuilt/selfbuilt_benchmark.yaml`
- `codeagent/benchmark/case_loader.py`
- `codeagent/benchmark/runner.py`
- `codeagent/benchmark/evaluator.py`
- `codeagent/benchmark/report.py`
- `codeagent/benchmark/environment.py`

BenchmarkRunner 的关键流程：

1. 读取 benchmark YAML。
2. 为 benchmark 创建独立 run directory。
3. 对每个 enabled case，将原始 case 复制到干净 per-run workspace。
4. 将 task config 中的 project path、input materials、visible paths、test command 映射到复制后的 workspace。
5. 隐藏 `evaluation`、`expected_result.json`、`oracle_tests` 等 runner-only 路径。
6. 调用 CodeAgent 运行 selected stages。

## 8. 已知问题、局限性与替代方案

### 8.1 已知问题和局限性

- BugsInPy 依赖 WSL、conda、Python 3.8.3 和官方 checkout；当前作为环境门控 optional case，不满足条件时记录 blocker。
- 真实 LLM 输出仍可能随模型服务、上下文和采样细节波动；系统通过 schema、prompt、重试、日志和回归 benchmark 降低风险，但不能完全消除。
- 当前主要支持 Python 项目和 pytest/unittest 测试命令；Java、多语言适配和 IDE 插件只保留扩展接口或设计预留。
- 生产级沙箱、Docker 化 SWE-bench harness 和大规模 SWE-bench Lite 不在本轮实现范围。
- wizard 当前已经覆盖“表单配置 + 直接运行 Agent”的半交互入口；完整审批恢复能力仍由 LangGraph interrupt 和 `resume` 支撑。
- wrapper path 前缀剥离仍基于文件系统存在性处理。如果未来需求要求从空项目新建顶层 `workspace/` 或 `project/` 目录，需要增加显式 opt-out 规则。

### 8.2 替代方案与取舍

- CLI 替代 IDE 插件：课程 prompt 提到 IDE 集成，但 SRS 和设计文档将本轮范围收敛到 CLI。CLI 更适合自动化测试、benchmark 和可审计产物。
- 通用测试命令替代只支持 pytest：SRS 强调 pytest，但 benchmark 中存在 unittest 命令，因此实现了 pytest 主解析器和 unittest/generic fallback。
- OpenRouter ChatOpenAI 替代供应商专用 SDK：LangChain 的 OpenAI-compatible 客户端能兼容 OpenRouter，便于统一模型配置。
- benchmark auto-approval 替代人工逐 case 审批：为了可重复自动评测，benchmark 模式自动批准必要副作用，但每次 auto-approval 都写入 decision trace。
- 环境 blocker 替代静默跳过 BugsInPy：缺少复杂外部环境时不伪装成功，而是在聚合报告中记录 blocker 和原因。

## 9. 后续可改进方向

- 增强交互式前端：将 wizard 扩展为完整运行控制台，支持在 CLI 中实时处理每个 interrupt。
- 增加 IDE/VSCode 集成：把 run directory、patch preview、approval 和 final report 接入编辑器界面。
- 增加 Docker 沙箱：为 shell、测试和 benchmark 提供更强隔离能力。
- 扩展 SWE-bench Lite 和 BugsInPy：提供自动环境准备、镜像缓存和更大规模评测。
- 扩展语言适配：在保留 Python 主线的基础上支持 JavaScript/TypeScript、Java 等项目。
- 增加模型评估矩阵：比较不同 OpenRouter 模型在成本、成功率、延迟和稳定性上的差异。
- 强化 LLM 输出诊断：将 malformed response、schema retry、prompt token 使用和失败类别做更细粒度统计。
- 增强报告可视化：为 benchmark success rate、case timeline、repair loop、token/cost 生成 HTML 或图表报告。
- 改进 resume 文案和 UX：去掉遗留 help 文案，提供 pending interrupt 列表和决策模板。
