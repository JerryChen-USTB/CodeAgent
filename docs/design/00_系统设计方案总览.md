# 00 系统设计方案总览

## 1. 设计目标

本系统设计面向“基于大语言模型的软件工程智能体”课程设计项目，目标是在需求规格说明书基础上，给出可以直接指导原型实现的系统设计方案。系统覆盖四个连续软件工程阶段：

```text
实现 → 测试 → 调试 → 修复
```

系统不是单次代码生成器，而是一个 CLI 驱动的软件工程智能体运行时。它能够读取需求、PRD、用户故事、API 规格、设计模型、项目骨架和验收条件，规划代码实现，生成或修改代码，生成并执行 pytest 测试，分析失败日志，定位根因，生成修复补丁，再次验证，并输出全过程报告。

## 3. 范围边界

### 3.1 范围内

| 范围 | 说明 |
|---|---|
| CLI 半交互模式 | `codeagent wizard`，逐步采集阶段、路径、测试命令和确认信息 |
| CLI 非交互模式 | `codeagent run --config task.yaml` 和阶段子命令 |
| 实现阶段 | 输入需求和项目骨架，输出实现计划、patch、变更清单、实现报告 |
| 测试阶段 | 生成测试方案，人工审核后生成测试 patch，执行 pytest，解析报告 |
| 调试阶段 | 读取失败日志，复现失败，搜索源码，定位可疑位置，输出根因分析 |
| 修复阶段 | 根据调试结果生成最小修复 patch，人工审批后应用，回归验证 |
| 日志和报告 | metadata、task_config、transcript、decision_trace、阶段报告、最终报告 |
| Checkpoint | SQLite 持久化，支持中断恢复和 HITL resume |
| Benchmark | 支持 benchmark.yaml 批量运行和成功率统计 |

### 3.2 范围外

| 范围外内容 | 说明 |
|---|---|
| IDE 插件集成 | 本设计只覆盖 CLI；不设计 VSCode/Eclipse/IntelliJ 插件，不设计 LSP |
| Git 工作区检查 | 不执行 git status，不检查 dirty 状态，不自动 commit，不依赖 git apply |
| 多语言完整支持 | MVP 只支持 Python + pytest；Java 仅做接口预留 |
| 生产级沙箱 | 只做基本路径限制、敏感文件跳过和命令审批，不承诺容器级安全隔离 |
| 生产级性能优化 | 以课程演示、可复现和可解释为目标，不追求高并发 |
| 测试方案与测试报告 | 本文档包不提供测试用例设计，只设计 Benchmark 模块结构 |

## 4. 总体设计原则

### 4.1 阶段子图优先

系统采用一个 LangGraph 主图和四个阶段子图。阶段子图分别对应实现、测试、调试、修复。每个子图内部有清晰的节点、条件边和工具调用循环。这样既满足课程“连续阶段”的要求，也能避免多 Agent 对话式架构带来的不可控性。

```text
MainWorkflowGraph
├── ImplementationSubgraph
├── TestingSubgraph
├── DebuggingSubgraph
└── RepairSubgraph
```

### 4.2 patch-first

所有项目源码和测试文件变更都必须先形成统一 diff，再进入人工审批节点；只有批准后才应用到项目目录。报告、日志、metadata、transcript、decision_trace 等运行产物直接写入输出目录，不需要逐项人工审批。

### 4.3 双层 HITL

系统采用两层人机协作机制：

| 层级 | 适用对象 | 说明 |
|---|---|---|
| 工作流级 HITL | 测试方案审批、patch 应用审批、测试命令审批 | 由 LangGraph interrupt 显式建模，审批结果影响后续路由 |
| 工具级 HITL | write_file、apply_patch、run_shell 等有副作用工具 | 由 LangChain HumanInTheLoopMiddleware 或自定义拦截器兜底 |

工作流级 HITL 是主路径；工具级 HITL 是安全兜底，防止模型绕过业务节点直接调用危险工具。

### 4.4 可审计而非隐藏思维链

系统不记录模型隐藏思维链。日志中保存的是可审计信息：

```text
用户输入
模型可见输出
结构化计划
工具调用和工具结果摘要
路由决策摘要
人工审批记录
失败原因和重试记录
```

这些信息足以支持课程验收、复盘和调试，同时避免依赖不可见的模型内部推理。

### 4.5 显式失败与可恢复

每个阶段都必须产生 `stage_result.json`。失败不是静默异常，而是结构化状态：

```json
{
  "stage": "repair",
  "status": "failed",
  "failure_reason": "修复后 pytest 仍有 2 个失败用例，已达到最大修复轮数",
  "artifacts": ["repair/after_test.log", "repair/repair_report.md"],
  "next_suggestion": "建议人工检查 fault_localization.json 中排名第一的候选文件"
}
```

## 5. 总体架构摘要

系统整体分为六层：

| 层 | 职责 |
|---|---|
| CLI 接入层 | 参数解析、wizard、进度展示、人工审批输入 |
| 任务配置层 | 解析 task.yaml、校验阶段连续性、初始化 run_id 和输出目录 |
| 工作流编排层 | LangGraph 主图和阶段子图，负责状态流转、条件路由、checkpoint |
| Agent 能力层 | Planner、Coder、TestDesigner、Debugger、Repairer、Verifier 等角色节点 |
| 工具执行层 | 文件扫描、读取、搜索、patch、shell、pytest 解析、报告写入 |
| 产物与状态层 | SQLite checkpoint、metadata、transcript、decision trace、阶段报告和最终报告 |

## 6. 自主实现与框架提供边界

| 能力 | 框架提供 | 项目自主实现 |
|---|---|---|
| 图式工作流 | LangGraph StateGraph、节点、边、条件路由、checkpoint、interrupt、streaming | 四阶段子图、阶段路由、状态结构、失败分支、修复闭环 |
| 模型调用 | LangChain 模型抽象、OpenAI-compatible 接入、消息抽象 | OpenRouter 配置、模型调用参数、提示词模板、结构化输出 schema |
| 工具调用 | LangChain tool 抽象和工具调用循环 | 文件工具、patch 工具、shell 工具、pytest 解析器、权限策略 |
| HITL | LangGraph interrupt、LangChain HITL middleware | 审批节点设计、审批数据结构、CLI 审批交互、审批记录 |
| 持久化 | LangGraph checkpointer、SQLiteSaver | run_id/thread_id 管理、输出目录组织、artifact index、resume 命令 |
| 报告 | 无直接框架能力 | 阶段报告、最终报告、transcript、decision_trace、benchmark 汇总 |

## 7. 核心运行闭环

```text
读取输入材料
→ 扫描项目结构
→ 规划阶段任务
→ 调用 LLM 生成结构化计划
→ 工具读取/搜索上下文
→ 生成 patch 或报告
→ 人工审批关键动作
→ 执行 pytest 或语法检查
→ 解析结果
→ 条件路由：成功 / 调试 / 修复 / 失败报告
→ 保存 checkpoint、日志、报告和产物索引
```

## 8. 推荐实现优先级

| 优先级 | 内容 |
|---|---|
| P0 | TaskConfig、CLI run/wizard、主图、四阶段子图骨架、文件读取/搜索、patch-first、pytest 执行与解析、报告输出 |
| P1 | SQLite checkpoint/resume、双层 HITL、修复多轮闭环、benchmark 批量运行、decision_trace |
| P2 | 结构化输出校验增强、上下文压缩、过拟合修复检测、Java Adapter 原型 |
| P3 | IDE 触发包装、LangSmith 可选观测、容器沙箱、多模型 fallback |
